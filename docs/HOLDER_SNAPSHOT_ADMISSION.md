18.10.2026. Локальный пакет после [исправлений ревью](PW_INTERIM_FIXES_20261018.md).
База Git `2b5d3d1`, поверх незакоммиченных исправлений. Реальные RPC, Pons,
контракты и сервер в этом пакете не использовались.

## Зачем

Pons перечисляет адреса, но одинаковые count/supply/as_of не доказывают,
что все страницы относятся к одному моменту. Не строим индексатор переводов:
проверяем перечисленные балансы разово на одном finalized блоке.

`src/holders/admission.mjs` требует неизменяемую snapshotPolicy:
scope, явно проверенную семантику обычного непрокси ERC20, runtime code hash,
maxHolders, maxRpcCalls и maxAgeSeconds. Значений по умолчанию для продукта нет.
Общая реализация ограничена 5000 адресами; более крупный снимок отклоняется.
Это техническая граница реализации, не утверждённый лимит числа холдеров PW.

1. Повторно валидируется полный Pons candidate; неполный список не допускается.
2. Проверяются chainId, finalized блок, окно периода, давность и runtime.
3. На одной высоте читаются totalSupply и balanceOf каждого адреса.
4. Все балансы должны совпасть с candidate, их сумма — с положительным totalSupply.
   Балансы не подменяются ответами RPC: при расхождении нужно собрать новый candidate.
5. После чтения проверяются канонический hash того же блока и сохранение finality.

Доказательство полноты условное: у проверенного обычного ERC20 все балансы
неотрицательны и суммируются в totalSupply. Если сумма перечисленных on-chain
балансов равна supply, ненулевых пропущенных балансов нет. Для нестандартного,
rebasing или proxy токена этого предположения без отдельного разбора недостаточно.
Поле semantics — явное подтверждение проверенной модели оператором, не анализатор
Solidity. Перед использованием на PW нужно подтвердить конкретный runtime/модель
Pons token; в этом пакете проверен только локальный ERC20 fixture.

## Запись и повтор

`admitHolderPreparation` читает уже сохранённый candidate и закреплённую политику.
После проверки под блокировкой строки БД повторно проверяет блок и revision.
В журнал попадает `snapshot.admitted` с candidateId, commitment балансов, policyHash,
сетью/контекстом, периодом, временем и block number/hash. Общий append не принимает
этот тип события без внутренней проверяющей функции. Прямой SQL/admin остаются
доверенными, как описано для финансового импортёра.

Один период может иметь один admitted candidate. Повтор того же запроса возвращает
старую ревизию после проверки блока; новый candidate не заменяет прежний.
Ошибки источника, stale/reorg, нехватка бюджета и гонка ревизии не создают запись.
Original candidate сохраняет `atomicity: unverified`: проверка добавляет отдельное
chain admission, а не переписывает историю источника.

## Стоимость

N адресов: N+6 явных JSON-RPC вызовов для полной проверки, ещё 2 перед COMMIT.
Если N+8 превышает maxRpcCalls, отказ происходит до первого RPC. Вызовы последовательные,
без скрытых retries и без фонового polling. HTTP-пагинация Pons имеет свой бюджет.
Повтор уже записанного допуска использует 4 проверки блоков, не перечитывает балансы.
Это число вызовов, не оценка цены/compute units конкретного провайдера.
Поддержка finalized и исторического eth_call у используемого бесплатного RPC ещё
не проверена. При недоступности или отказе запросов допуска не будет.

## Граница финансового исполнения

Это проверенный снимок для будущего расчёта, **не авторизация начислений/выплат**.
В ledger не добавляются round, долги или переводы; executionEnabled=false.
Fixture-round запрещён для профиля с snapshotPolicy. Preview снимает только
предупреждение о непроверенной целостности выбранного admitted snapshot;
проверка фонда, ETH-порог и финансовое исполнение остаются отдельными blockers.

В текущей репетиционной схеме используется finalized блок между dueAt и следующим
30-дневным сроком; maxAgeSeconds ограничивает свежесть. Политика допустимой задержки
реального месячного cutoff ещё НЕ утверждена. По истечении окна preview показывает
holder-period-missed. Свежий снимок не назначается задним числом пропущенному месяцу.
Период не продвигается от одного факта допуска; это задача будущего round/seal.

RPC и проверенная модель токена остаются границами доверия. Проверяется стабильность
finalized block hash до/после чтений, не криптографические storage proofs. Допуск
сохранённого блока нужно повторно сверить перед будущим seal после рестарта.
Накопительный vault по-прежнему без вывода, production-launch PW заблокирован.
