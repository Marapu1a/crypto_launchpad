# Инкрементальный реестр билетов

09.10.2026. Пакет поверх `32d10ea`. Код: `server/shared/ticket-ledger.mjs`,
миграция `004_ticket_ledger.sql`. Команда проверки: `npm run test:shared:tickets`.

Новый путь хранит события, начисления, кошельки, подтверждения и snapshots
отдельно. Он работает параллельно с прежними `scanTickets` и `ticket-shadow`:
их состояние не мигрируется и финансовый worker не переключается.

## Таблицы

| Таблица | Содержание и права runtime |
| --- | --- |
| ticket_ledgers | Неизменный профиль/source, отдельный курсор; UPDATE только курсора |
| ticket_events | Первоначальное решение и исходные transaction/receipt, checksum; только INSERT |
| ticket_credits | Единственное начисление на candidate ID, сумма, wallet, credited block и проверенное событие; только INSERT |
| ticket_wallets | Накопленный net debit; UPDATE суммы, билеты и остаток вычисляются точно через BigInt |
| ticket_commitments | Уникальный bundle hash и полное подтверждающее свидетельство; только INSERT |
| ticket_snapshots | Label, неизменный вход/cutoff и snapshot; только INSERT |

Ключи и FK включают project/module, FORCE RLS действует на все шесть таблиц.
У `lp_api` и `lp_ingest` нет доступа. У `lp_jobs` нет DELETE и изменения исходных
событий, начислений, commitments, snapshots или профиля. Доверенный scope runtime
остаётся частью границы доступа; это не защита от компрометации его DB credentials.
Профиль/bundle/подписанные хешем структуры сохраняют точный JSON-текст.

## Новые блоки и поздние подтверждения

`registerTicketLedger` проверяет те же локальные bindings/runtime/anchor,
что shadow-адаптер. Для сравнения используется та же версия профиля и модуля
`local-ticket-shadow-v1`; это ещё не production adapter.

`applyTicketLedger` читает только блоки после собственного курсора, максимум 500
за транзакцию. Распознанное событие добавляется неизменно. Обычная подходящая
покупка создаёт credit и увеличивает сумму только соответствующего кошелька.
Порог берётся из неизменного профиля; float и округления сумм не используются.
Переполнение числа билетов uint128 отклоняет транзакцию.

Поздний commitment выбирает по составному ключу только перечисленные покупки
(не больше 50), их исходные доказательства и существующие credits. На этом
ограниченном наборе используется прежняя `creditedEvents`: проверяются authority,
runtime, домен, calldata, исходный платёж и историческая позиция покупки.
Полная прежняя история не загружается и не пересчитывается.

Первое начисление закрепляет `creditedAt`. Повторная доставка покупки новым
commitment проверяется, но уникальность credit не даёт повторно увеличить сумму.
Повтор уже сохранённого bundle hash запрещён составным PK. Первоначальный
WAITING_RECOGNITION остаётся первоначальным решением в ticket_events.

Изменения events/credits/wallets/commitments/cursor входят в **одну транзакцию**.
Блокировка отдельной ledger-строки сериализует исполнителей одного модуля.
Проблема файла/доказательства/записи откатывает весь пакет. Проекты независимы.
Raw source блокируется совместно с прежними consumers; reorg/halt останавливает
обработку. Автоматического rollback/replay нет.

## Снимки и чтение

`readTicketLedger` получает курсор и суммы одним SQL-запросом, чтобы конкурентное
применение не смешивало разные версии. Это диагностическое чтение возможно и
при halted source; результат не является разрешением финансового исполнения.

`freezeLedgerSnapshot` суммирует credits по **credited_block <= cutoff**, а не
по исходному блоку покупки. Для этого есть индекс project/module/credited_block.
Текущий wallet cache не используется для исторического cutoff. Суммирование
истории при создании нового снимка выполняется БД; оно не происходит на каждом
новом блоке. Полный пересчёт истории в JS для применения больше не нужен.

Участники и snapshot hash совпадают со `snapshotTickets`. Label нельзя повторно
использовать с другим cutoff/consumed. Проверяются ветка и hash снимка.
Как и прежде, consumed передаёт внутренний caller: это **снимок сравнения**,
не on-chain cycle, reservation или авторизация worker.

## Проверки

В отдельном PostgreSQL и на двух собственных токенах localhost31337 сравниваются
новый ledger, прежний JSON shadow и файловый scanner. Проверены opening/direct
покупки, разные пороги, carry, late credit, повторные подтверждения, frozen cutoff,
consumed ranges, независимость B при сбое A, конкурентные применения и restart.

Есть намеренный сбой триггера **после** новых событий/credit/wallet, при записи
курсора: откатывается весь пакет, после retry появляется ровно одно начисление.
Проверены RLS, запреты удаления, неизменность исходного WAITING и первого
creditedAt, runtime/instance drift, reorg halt и backup/restore всех шести таблиц.

Счётчики применения показывают объём работы, а не production benchmark:
no-op retry — 0 новых блоков/старых доказательств; повторная доставка в одном
блоке — 1 блок, 1 прежняя покупка, 0 новых credits. Метрики находятся в
`ticketShadow.ledgerStats` отчёта.

## Границы

Прежний shadow остаётся эталоном, автоматического переноса накопленных состояний
нет: новый ledger строится из общей raw истории. Shared raw storage и доказательства
пока не очищаются/не архивируются; capacity/retention требуют отдельной проверки.
Защитные RPC-чтения runtime/getters/hash сохранены, полные receipts не скачиваются
повторно. Сетевые таймауты/постоянный scheduler, production finality, неизвестные
маршруты/pool и QIANQI shadow/cutover остаются открыты.

Следующий предлагаемый пакет — изолированный финансовый журнал в PostgreSQL:
запись намерения до отправки, восстановление и запрет двойного исполнения на
локальной репетиции. QIANQI production и реальные отправки этим пакетом не затронуты.
