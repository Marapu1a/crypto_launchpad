## Что делает исполнитель

`server/shared/production-worker.mjs` обслуживает один проект за pass:

1. Проверяет сеть, anchor, runtime hashes, связи factory/curve/collector,
   quote/6 decimals, программу, adapter, recognition publisher и экономику.
   Доли, порог билета, интервал, призовая корзина и получатели берутся из
   закреплённой policy проекта. Нет универсального хардкода 80/15/5.
2. Читает последовательные finalized-блоки, транзакции и receipts. Плательщик
   и сумма определяются из calldata/событий/переводов токенов, без старого API.
   Сохраняет исходные решения и evidence, проверяет непрерывность и каноничность.
3. Отдельный publisher публикует commitment пакета до 50 проверенных покупок.
   Билет учитывается на finalized-блоке этого подтверждения. Notice контракта —
   24 часа после создания recognition. Неизвестному маршруту билет не выдумывается.
4. Собирает creator fees: curve → escrow → collector → splitter → призовой
   фонд/команда/операционные расходы. Сначала доставляет имеющиеся остатки.
   Операционная доля остаётся в USDG; автоматической покупки native gas нет.
5. При достаточном фонде, участниках и истёкшем интервале фиксирует dataset,
   budget и finalized checkpoint. Проверяет свежесть chain/drand и настоящий
   BLS latest beacon до freeze. После freeze работает только с выбранным раундом.
6. Подтверждает proof, доставляет seed, выполняет settle, погашает rewards.
   После settle начинается следующий интервал; отсутствие победителя допускается.

Финансовые чтения planner относятся к одному finalized-блоку. Дополнительно
перед freeze проверяется неизменность live-бюджета. Admission повторяется перед
подготовкой, подписью и broadcast. Снижение наблюдаемого finalized ниже уже
подтверждённой операции приводит к ожиданию. Изменение её канонического hash —
ошибка, а не повод переписать историю.

Линии funding/recognition/draw чередуются: постоянный поток новых покупок
не должен бесконечно отодвигать розыгрыш. Подготовленная операция сначала
заканчивает reconciliation; следующая не подписывается поверх неизвестного исхода.

## Состояние и восстановление

Существующая строка `production_senders` хранит журнал executor и вложенные
planner/ledger/cycles/bundles/publisher journal. Всё записывается с checksum и
CAS revision под одной PostgreSQL session lease. Policy менять runtime не может.
Snapshot и bundle сохраняются **до** подписи; raw-транзакция — **до** broadcast.
После обрыва используется та же подпись, а mined receipt ждёт finalized.

Миграция `012_production_wallets.sql` резервирует executor и publisher в общей
уникальной паре `(chain_id,sender)`, включая пересечение разных ролей между
проектами. Проверяется не только пустая БД, но и backfill заполненной миграции 011.
API/jobs не читают эти таблицы. У каждой программы свои snapshots, обязательства,
RNG и билеты. Общая роль БД по-прежнему способна переключать project context:
это защита запросов, не изоляция от скомпрометированного владельца runtime/ключей.

`runProductionProjects` возвращает отдельный результат каждого проекта:
ошибка одного не прерывает проход соседей. Отправки по одному проекту
последовательны. Неуспешный receipt блокирует его журнал до reconciliation;
ошибка получателя не стирает призовое обязательство. Автоматического обхода
застрявшей подписанной операции или замены nonce нет.

## Проверка

Команды:

```text
npm run test:production-worker
npm run test:production-contracts
node --test tests/unit/production-worker.test.mjs tests/unit/executor-keystore.test.mjs
npm run test:shared
```

Стенд — отдельная in-process сеть 4663, отдельный кластер PostgreSQL и
общеизвестные тестовые кошельки Hardhat. Ни public RPC, ни реальные ключи
для финансовых тестов не используются. Два тестовых токена имеют разные
программы, подписантов, получателей и наборы покупателей.

Основные сценарии:

- прямые покупки → комиссии 2% → split 80/15/5 → фонды 64 и 96 тестовых USDG;
- подтверждения покупок отдельными publisher, порог билета 10 тестовых USDG;
- конкурентный pass возвращает busy; принудительная потеря DB session после
  сохранения подписи запрещает broadcast; второй проект продолжает работу;
- возврат к тому же hash, ожидание receipt-finality без второй подписи;
- поздняя покупка и отдельно задержанная финальность её подтверждения:
  frozen snapshot прежний, дополнительный билет переходит следующему циклу;
- proof выбранного раунда, settle и claim обоих токенов; повторные проходы
  не дают второй выплаты; чужой publisher/искажённая история не допускаются.

## Границы и следующий пакет

- Finality моделируется тестовым observer, это не проверка консенсуса Orbit.
  Timing 3600/30/30/1800/30 — только параметры стенда, боевые ещё не утверждены.
- Pons в этом тесте — fixture. Он проверяет проводку creator fee и прямую покупку,
  а не всю реальную кривую/снайп-налог/base fee/пулы. Чистый decoder также содержит
  opening buy, но этот сценарий здесь не доказан. Остальные маршруты и graduation
  не объявляются закрытыми: сохраняются неподтверждённые события без билетов.
- Все подходящие покупки проходят единый recognition gate; нет обратной вставки
  билета в старый draw. Поддержка нового ранее неизвестного маршрута требует
  отдельно проверенной версии decoder и процедуры перехода policy.
- Ledger/evidence сейчас находятся в приватном состоянии проекта. Чтение блоков
  выполняется на проект; подключение общего chain reader, проекций API и проверка
  стоимости/роста хранилища нужны при включении постоянного runtime.
- Нет production daemon, public launch route, IPFS/wallet onboarding или нового
  публичного сайта. Ошибки runner возвращаются вызывающему коду; Telegram для
  новых проектов этим модулем ещё не подключён. QIANQI обслуживается прежним путём.
- Адрес настоящего USDG и точные deployed runtimes должен допустить deployment
  профиль. Одни лишь имя/decimals токена этого не доказывают.
