# Pons: комиссии, данные сайта и бюджет RPC

14.10.2026, рабочее дерево поверх e3585b6. Локальный пакет, не production release.
Продолжает [QIANQI scheduler](QIANQI_PONS_SCHEDULER.md).

Следующий выполненный локальный пакет — [обслуживание по изменениям Pons](PONS_EVENT_SERVICE.md):
пропуск пустых RPC-проходов и receipts собственных публикаций. Ниже сохранены
измерения и границы до этого изменения; актуальный статус — в CURRENT_CONTEXT.

## Реализовано

- `server/adapters/qianqi/pons-funding.mjs`: существующий сборщик Pons подключён
  к новому scheduler. Адреса, code hashes, кампания, получатели и доли закреплены
  в identity журнала. Используется прежний funding pass и тот же журнал транзакций.
  После отправки план перечитывается; в пустом проходе один план используется повторно.
- Стенд QIANQI получает 600 USDG из escrow и 600 через sweep curve:
  1080 в vault, по 60 двум получателям. В vault это 540 Short, 440 Current,
  100 Next. Прямого тестового пополнения vault в этом сценарии больше нет.
  Venue — модель Pons, не настоящий публичный контракт; sweepPool отдельно не прогонялся.
- `pons-projection.mjs`: деньги читаются на finalized checkpoint; билеты — из
  перенесённого учёта Pons. Схемы прежние: `promo-overview-v1` и
  `promo-wallet-status-v1`. Видны фонд, история, выплаты, open/consumed/frozen,
  сумма покупки и число добавленных пар билетов с учётом остатка.
  Старые кредиты сохраняют получателя/сумму; новые объясняются порядком admission.
- `pons-public-store.mjs`: отдельный публичный файл, checksum и атомарная замена.
  Reader подключается к существующему `createServer(config,{reader})`:
  `/v1/overview`, `/v1/wallets/:address`. HTTP не обращается к RPC.
  Истёкший срок контракта или Pons даёт `stale`, повреждение файла — `unavailable`.
  Время старого снимка не переписывается текущим временем посетителя.
- Проверены 200 рендеров и три HTTP-запроса: ноль RPC. Испорченный файл
  отклоняется; исправленный снова читается. Сторонняя смена эпохи блокирует
  новый снимок до обработки соответствующих receipts.

Исторические даты начала/завершения draw в новом overview пока `null`;
ссылки на транзакции сохраняются. Финансовая история проверяется чтением известных
draw/reward, поэтому стоимость проекции растёт с их числом.
Snapshot не содержит signer или signed payload. UI не изменён и не опубликован.

## Измерения и пределы

`tests/contracts/rpc-meter.mjs` считает вызовы на границе локального узла,
включая вспомогательный HTTP reader. Fixture setup вне измерения.
Сохраняются только имена методов и числа. Заведомо прерванные crash-проходы
не входят в сумму завершённых проходов.

| Сценарий | QIANQI | v2 dual, движок IGW |
|---|---:|---:|
| Один спокойный worker pass, RPC | 87 | 417 |
| Построение public snapshot, RPC | 47 | 40 |
| Worker pass, оценка CU | 994 | 5108 |
| Snapshot, оценка CU | 940 | 588 |
| Все завершённые passes теста, CU | 47002 (18 passes) | 677828 (28 passes) |

Последняя строка включает активные действия и проверки восстановления;
это не гарантированная цена одного реального draw. QIANQI использует near-certain
fixture rules; v2 — два модуля, хотя live IGW имеет только Short.
Состояния/число участников у стендов разные; сравнение не является benchmark контрактов.

Для двух стендов, worker + projection с одинаковой периодичностью, 30 дней простоя:

| Интервал | Оценка CU/месяц |
|---|---:|
| 5 минут | 65 923 200 |
| 15 минут | 21 974 400 |
| 30 минут | 10 987 200 |

Это сценарии, **не включённые настройки**. При 15/30 мин нужно отдельно согласовать
срок актуальности снимка: текущий default 660 секунд честно станет stale.
Покупки можно замечать чаще через Pons без RPC; пробуждение worker по изменению
отчёта и объединение проверок — следующий пакет.

Скрипт `scripts/report-pons-rpc-budget.mjs QIANQI_REPORT V2_REPORT` создаёт новый
отчёт в `.local/test-results/` без сети. Цена методов сверена 14.10.2026 с
[таблицей Alchemy](https://www.alchemy.com/docs/reference/compute-unit-costs):
`eth_call` 26 CU, block/code/receipt 20 CU, `eth_chainId` 0 CU.
[Free](https://www.alchemy.com/docs/reference/pricing-plans) — 30 млн CU в месяц.
Batch не отменяет стоимость методов. `hardhat_*` и fixture `evm_*` исключены;
локальный `eth_sendTransaction` оценён как `eth_sendRawTransaction`.
Активность, повторы, другие приложения, история, число участников — добавочная
нагрузка. Месячный лимит не заменяет ограничение CU/сек. Это не счёт провайдера.

## Граница следующего release

Scheduler всё ещё допускает только локальный Hardhat chain4663.
Reader готов для HTTP API, но production entrypoint, периодическое создание
снимков и systemd wiring не переключены. Файлы конфигурации/кошельки/ключи
с сервера не копировались. Проверенный локальный пакет не является готовым deployment.

Перед включением на бесплатном RPC остаётся:

1. Сократить повторные проверки v2 и редкие пустые проходы; ввести общее
   расписание worker/projection, пробуждение от Pons, throughput/backoff и
   измеряемый лимит расхода аккаунта. При активной торговле текущий бюджет
   нельзя экстраполировать из одного quiet pass.
2. Убрать диапазонный поиск публикаций в старых валидаторах QIANQI или явно
   ограничить/измерить его. `paged-log-read.cjs` допускает 10000 блоков;
   ранее проверенный Free endpoint — 10. Это не поиск покупок, но блокер
   совместимости. Предпочтительны известные receipts собственных публикаций
   с прежней сверкой root/count/hash и восстановлением после рестарта.
3. Production guard и запуск со свежим состоянием, сверкой прежних обязательств
   и журналов. Миграция активного незавершённого job пока не реализована.
4. Read-only квалификация выбранного бесплатного endpoint и отдельный выпуск.
   Не снимать systemd-запреты и не запускать старые индексаторы.

QuickNode не опрашивался, услуги не покупались, VPS не запускался.
