# PW: единая локальная репетиция

PW local adapter теперь использует [managed holder vault v2](HOLDER_GOVERNANCE.md).
Репетиция дополнена сменой publisher посреди списка; исторические отчёты ниже
сохраняют свои прежние границы проверки.

18.10.2026. Рабочий пакет поверх `2b5d3d1` и предыдущих локальных изменений.
Команда: `npm run test:pw-rehearsal`. Нужен локальный PostgreSQL 17; тест создаёт
свой кластер. Реальные RPC, кошельки и сервисы не используются.

## Что соединено

1. `deployPwLocalGraph` читает профиль PW и явные тестовые параметры. Проверяет
   ETH, creator tax 3%, split 60/20/20, месячные периоды, один призовой слот и
   отключённый buyback. Принимает только свежий изолированный Hardhat instance.
2. Разворачивает настоящие collector, splitter, payout vault и NativeShortProgram.
   Создание ERC20/curve выполняется локальной фабрикой-моделью с registry Pons;
   затем проверяются привязки collector. Manifest сохраняет адреса, runtime-хеши,
   сборки, профиль и параметры.
3. Покупки ETH в модели curve начисляют ровно 3% creator tax. Комиссия проходит
   curve → escrow → collector → splitter → фонды 60/20/20.
4. Модель ответа Pons проходит через существующие `advancePonsAccounting` и
   `snapshotPonsTickets`. Состояние билетов сохраняется и читается заново.
5. Через 30 дней контракт фиксирует участников. Исторический drand beacon
   проверяется настоящим BLS verifier; после сохранения proof доставка
   возобновляется без нового seed. Розыгрыш завершается; выигрыш выплачивается
   либо фонд переносится. Результат не подбирается для принудительной победы.
6. Тот же collector/vault и фактические покупки используются для двух периодов
   холдеров, admission, PostgreSQL-планов, долгов, выплат и их сверки.
7. Отдельные дочерние Node-процессы читают сохранённую транзакцию до отправки и
   подтверждают её после потери ответа. Им не передаются signer или память
   родительского процесса. БД и локальная цепь продолжают работать.

Отчёты, launch manifest и ticket checkpoint находятся в
`.local/test-results/pw-rehearsal-*/`. Тестовый тикер `PWTEST` и суммы в wei
не являются выбранными параметрами настоящего PW.

## Поиск пропущенных выплат

`scanHolderPayments` работает по запросу и читает только Paid своего vault.
Начало диапазона берётся из зафиксированного funding profile. Миграция 019
хранит cursor и канонический checkpoint под RLS.

- По умолчанию до 500 блоков и 50 транзакций; предельные настройки — 2000/100.
  Дополнительно ограничен размер списка логов. Это ограничения одного вызова,
  а не постоянный фоновый опрос.
- Только finalized диапазон. Перечень транзакций из логов проходит повторную
  проверку receipt через внутренний resolver либо внешний importer.
- Импорт записывается раньше cursor. При обрыве уже импортированные receipts
  проверяются повторно без повторного начисления; cursor не перескакивает ошибку.
- Ошибка RPC/превышение бюджета оставляет диапазон непройденным. Конкурирующее
  изменение cursor требует повторить вызов. Reorg checkpoint останавливает обход.
- Доверяем полноте ответа RPC getLogs: скрыто обрезанный успешный ответ одним
  cursor проверить невозможно. Последующая сверка totalPaid обнаруживает
  недостающие выплаты, но это не доказательство надёжности конкретного провайдера.

## Что эта репетиция не доказывает

- Реальная фабрика Pons/CREATE2, её permissions, экономические настройки и API
  здесь моделируются. Это НЕ mainnet fork-проверка запуска.
- Локальный adapter не подключён к публичной форме/production coordinator.
  Обычный launch path продолжает блокировать PW; admission не ослаблен.
- Создание deployment graph ещё не имеет самостоятельного resumable coordinator;
  перезапуск проверен для обслуживания уже созданного графа, не посреди deployment.
- Historical beacon доказывает исполнение verifier, не неизвестность будущего seed.
- Модель curve не воспроизводит рыночную цену, базовую комиссию Pons и graduation.
- Тестовые роли совмещены, ключи публичные Hardhat. Нет утверждённого управления
  publisher, газовых бюджетов, production runtime и cutoff-политики. ETH-пороги
  после репетиции утверждены в правилах PW; повторный прогон с ними ещё предстоит.
- Это запуск по тестовой команде, не установленный сервис с расписанием.
- Проверены небольшие списки; оценка газа и времени для больших списков впереди.

Следующий практический шаг — проверить утверждённые суммы и выбрать модель управления,
проверить реальную фабрику/runtime чтением, затем собрать production admission
и журнал deployment. После этого — отдельное решение владельца о выпуске.
