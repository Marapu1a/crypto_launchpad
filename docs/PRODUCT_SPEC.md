# Платформа и первый шаблон

## Назначение платформы — уточнение владельца 07.10.2026

Собственный UI запускает токены непосредственно через контракты Pons, без
необходимости проходить их UI. Пользователь настраивает базовую экономику,
выбирает дополнительную финансовую механику и получает развёрнутый и обслуживаемый
проект. Цель — простой и быстрый запуск сложных финансовых программ.

Розыгрыши — первый модуль, а не граница продукта. Новые механики добавляются
проверенными версиями шаблонов; произвольные сочетания и пользовательский Solidity
пока не входят в MVP. Конкретные механики сверх розыгрыша ещё не выбраны.

Настройки Pons ограничены возможностями протокола; собственный интерфейс не
даёт прав менять недоступные параметры. Дополнительные правила реализуются
нашими контрактами и обслуживанием. Первый пакет должен разделить эти области.

## Первый шаблон

Порядок работ уточнён владельцем 07.10.2026: сначала воспроизвести доступные
функции запуска Pons, проверить и сохранить базовую версию. Собственные
финансовые механики добавляются после неё; см. [PONS_BASELINE](PONS_BASELINE.md).

Источник принятых правил: [PLATFORM_START](../PLATFORM_START.md).

Одна кодовая база обслуживает независимые токены. У каждого свои контракты,
средства, билеты, настройки, случайность и журналы. Действующий QIANQI не мигрирует.

Решение владельца 07.10.2026: первый лаунчпад — Pons. PAIR сохраняется как
возможная последующая интеграция. Точную версию Pons, адреса и условия нового
запуска проверяем перед реализацией интеграции; исторические настройки не переносим автоматически.

Первый пример: USDG; creator fee 1%, если поддерживается лаунчпадом;
минимум 100 USDG реально полученного фонда и минимум 6 часов между распределениями.
Весь frozen фонд делится между одним победителем и командой.
Уточнение владельца 07.10.2026: 50/50 — начальное значение, не хардкод.
При создании программы доля победителя свободно задаётся ползунком;
доля команды автоматически дополняет её до 100%. Выбранные доли сохраняются
в параметрах конкретного экземпляра и фиксируются вместе с правилами цикла.
Шаг ползунка и крайние значения уточнить при проектировании. Возможность менять
доли после запуска — отдельное открытое решение, не право менять frozen цикл.
Нет ветки розыгрыша без победителя при наличии участников.

Каждые накопленные 100 номинальных USDG подходящих покупок дают билет.
Остаток до билета переносится. SELL билеты не отменяет; transfer не считается BUY.
Вес адреса с x билетами: x/(x+1); вероятность — вес / сумму весов.
Это не защита от нескольких адресов одного человека.
Все билеты зафиксированного набора расходуются после завершения цикла.
Поздние покупки и поступления относятся к следующему набору/бюджету.

Бюджет, участники, веса и правила фиксируются до раскрытия случайности.
Нет reroll/reset; призовые и командные обязательства не расходуются на gas.
Сбой получателя или RPC не должен менять результат или создавать повторную отправку.

## Открытые решения — пока не реализация

| Вопрос | Предложение для обсуждения |
|---|---|
| Отсчёт интервала | От фиксации предыдущего цикла по block timestamp; первый — от активации экземпляра |
| Нет участников | Копить и ждать; не запускать пустой draw, не платить команде отдельно |
| Право на доли | Резервировать бюджет при freeze; обе доли становятся claimable после окончательного результата |
| Отказ получателя | Раздельное получение долей; ошибка одной выплаты не блокирует другую |
| Округление долей | Победителю floor(fund × выбранная доля), команде остаток; явно показать правило |
| Изменение правил | Версия механики неизменна; изменения разрешённых параметров только для будущих циклов с notice |
| Диапазоны и адрес команды | Определить при проектировании, отдельно решить возможность смены адреса |
| Gas и обслуживание | Отдельный бюджет оператора, без использования обязательств; комиссия платформы не согласована |

Точные диапазоны, notice, custody и схема создания экземпляров ещё не выбраны.
Предложения в таблице не являются согласованными финансовыми правилами.

## Актуальное направление — 08.10.2026

Платформа прежде всего личный конструктор владельца. По его уточнению основой
служат механики QIANQI с гибкими настройками Short/Monthly, BUY на билет,
распределения creator fees и числа победителей. Это заменяет ограничение первым
единственным шаблоном 50/50 выше; исходный brief остаётся историческим документом.
Статус, реализованные параметры и открытые решения — [DRAW_MODULE](DRAW_MODULE.md).
Пока реализована только модель конфигурации и расчёт корзины, без денежных операций.
