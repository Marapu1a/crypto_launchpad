# QIANQI: расход RPC после продажи — 20.10.2026

Локальный пакет исправления. Production не изменён. Рабочая база `0a1b596`;
производственный runtime — `pons-e2731ea-20261014`.

## Подтверждённое состояние

Продажа `0x2742faf912f03732d28acb73d3f4f85d13d74578c930f382a90e8894f5243fcf`
поступила в Pons с `decision=sale-no-ticket-change`. После неё существующая

содержал кредит 3,035390 USDG фонду и 0,337264 USDG адресу команды/обслуживания.
Подтверждённый finalized блок — 93541401. Это снимок состояния, не обещание
текущего баланса и не разрешение на ручную отправку.

Монитор сообщил внимание к проекту в 16:17:51 МСК, затем устаревший API в
16:23:00. Локальный общий лимит — 2000 RPC-запросов за час — был исчерпан.
API отвечал HTTP 200/status=stale. IGW оставался в ожидании, его API был свежим.
Около 17:16 QIANQI самостоятельно восстановился, затем снова исчерпал бюджет.
Это локальный бюджет приложения, не доказательство исчерпания квоты Alchemy.

## Причина лишней работы

- Полученный receipt ещё не означает финальность. Старый планировщик повторял
  полную сетевую подготовку при ожидании уже сохранённого receipt.
- Обновление публичного снимка запускалось даже для `receiptFinality`.
- Ожидание финальности сразу после успешного сбора комиссии попадало в общий
  `fundingError`, после чего проход продолжал читать контракты и строить снимок.
- Причина ошибки сбора терялась в общем `waiting`. Повторы шли через 15 секунд.
- Проверка допуска продолжала читать контракты даже после обнаруженной задержки
  времени/финальности. Бюджет мог скрываться под `observationUnavailable`.

Отдельное read-only измерение действующего допуска дало 193 запроса:
97 eth_chainId, 63 eth_call, 26 eth_getCode, 6 eth_getBlockByNumber,
1 eth_getStorageAt. Допуск совпал с профилем. Перед отправкой текущий код
проверяет его дважды. Это измерение одного допуска, не полная трасса инцидента.
Диагностика использовала общий persistent budget и ограничение числа чтений;
подписания и отправки диагностикой не выполнялись.

## Исправление

1. Под блокировкой и после проверки сохранённого состояния незавершённая
   финальность проверяется до дорогой подготовки: chain и finalized head.
   Повтор — не раньше минуты. После достижения блока остаётся обычная проверка
   receipt, canonical hash и применение событий. Один номер блока не начисляет
   билеты и не завершает платёж.
2. Ожидание после успешной транзакции явно возвращается как `receiptFinality`.
   Оно не начинает следующий платёж и не пересобирает публичный снимок.
3. Бюджетные ошибки проходят до общего планировщика с `retryAt`; повтор ждёт
   конца окна. Другие ошибки сбора видны в health и получают паузу пять минут.
   Обслуживание уже существующих обязательств сохраняется.
4. Неверное время/отставшая финальность прекращают допуск до чтения контрактов.
   Проверки перед реальной отправкой, лимит и финансовые правила сохранены.

Публичный снимок во время ожидания может оставаться устаревшим: исправление
не выдаёт неподтверждённые средства за актуальные. Полный допуск перед отправкой
по-прежнему дорогой; этот пакет устраняет повторную работу во время ожидания,
а не объявляет нулевой RPC при финансовом исполнении.

## Проверка и выпуск

- Unit: ожидание/ошибки/неверная сеть, часовая симуляция таймера, независимость
  проектов, persistent budget, сохранение подписанной транзакции при отказе.
- Контрактный сценарий отдельного сохранённого receipt: четыре обращения к
  локальному узлу, включая одно rehearsal-only hardhat_metadata; ноль eth_call
  и eth_getCode. После финальности применяется тот же receipt, новых отправок нет.
- Полный сценарий обоих контроллеров PASS: freeze, RNG, settlement, выплаты,
  сохранённые билеты, сбои после подписи/отправки/receipt, поздняя покупка,
  смена эпохи и дополнительное поступление с задержкой финальности. Три прохода
  после рестарта потребовали по 6 запросов, без eth_call/eth_getCode и дубля оплаты.
  Неизменный источник после доказанного idle даёт 0 RPC.
- Проверки текущего пакета: 47 unit/admission/recovery сценариев и два контрактных
  сценария прошли. Полный интеграционный отчёт:
  `.local/test-results/qianqi-pons-2026-10-20T15-26-12-215Z/report.json`.
  Последующая небольшая проверка валидации состояния перед ожиданием покрыта
  отдельным контрактным тестом `saved mined receipt`; полный прогон повторно
  без причины не запускался.
- Финальный пакет: `.local/qianqi-rpc-fix-20261020-v2/` (payload, changes.patch,
  manifest.json). Первая сборка сохранена отдельно. Применимость патча к
  `e2731ea`, совпадение серверных исходных хешей и синтаксис семи файлов PASS.
  Существующая тестовая фикстура дополнена явным `asset: USDG` для текущего
  multi-asset кода; это не миграция production-профиля.

Пакет выпуска строится поверх точной действующей версии, только из семи файлов
исправления. SHA-256 шести исходных файлов сверены с сервером. Более новые модули
PW, изменения подписки и конфиги не входят в этот пакет. Изменение кода требует
отдельного выпуска и проверки службы; текущие журналы и бюджет не сбрасываются.
