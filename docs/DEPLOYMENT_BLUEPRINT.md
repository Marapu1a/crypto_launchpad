# Первый экземпляр: проект графа запуска

Статус после уточнения владельца 07.10.2026: будущий этап собственных модулей.
Сначала реализуется и проверяется [базовый запуск Pons](PONS_BASELINE.md).
Описанные ниже собственные контракты для базового запуска не нужны.

07.10.2026. Предложение архитектуры после [исследования Pons](PONS_FEE_FLOW.md).
Это не исполняемый deployment-пакет: новые контракты и calldata ещё не написаны.
Финансовые предложения требуют решения владельца; схема не разрешает отправки.

## Состав

- `C`: отдельный collector, получает USDG через escrow и передаёт только программе.
- `R`: программа первого шаблона: накопления, frozen budget, snapshots, результат,
  отдельные обязательства победителю и команде. Название контракта пока условное.
- `G`: RNG adapter для одной программы, без старого обязательного Short/Monthly.
- Индексатор/keeper/API: отдельное состояние и журнал экземпляра.
- Pons token/curve/escrow/hook: существующая внешняя инфраструктура.

Не добавляем отдельный registry только потому, что он был в QIANQI: участие
основано на подходящих покупках. Способ допуска BUY и фиксации snapshots нужно
спроектировать явно; новый on-chain policy source добавит отдельный шаг, если нужен.

## Порядок

| Шаг | Действие | Проверяемый результат |
|---|---|---|
| 0 | Локально сохранить metadata, параметры, роли, chainId, профиль Pons и salt | Стабильный draft и версия правил |
| 1 | Прочитать gate/config/quote/fees/economics/bindings; оценить расходы | Пользователь видит реальные условия |
| 2 | Рассчитать адреса C/G/R от последовательности CREATE кошелька; предсказать Pons token/curve с C как fee recipient | Замкнутый план адресов без циклического CREATE2 поиска |
| 3 | Развернуть C, затем G, затем R с перекрёстными ожидаемыми адресами | Все наши контракты существуют до начала торговли; ещё не активны |
| 4a | Без opening buy: прямой factory.launchToken | TokenLaunched и правильный collector |
| 4b | С opening buy: при необходимости approve USDG router, новый preview, затем launchAndBuy | Создание+покупка атомарны; refund и результат проверены |
| 5 | Сверить receipts, runtime и on-chain record; финализировать bindings C/R | Программа привязана к правильному token/curve/quote и версии правил |
| 6 | Установить BUY genesis по фактическому launch block/его parent, replay с launch block включительно | Учтены ранние сторонние покупки и opening buy, если маршрут поддержан |
| 7 | После проверки finality/history/gas включить keeper/API | Страница проекта показывает готовую программу |

Рассчёт собственных адресов в шаге 2 не зависит от constructor calldata обычного
CREATE. Поэтому сначала известен C, затем можно вычислить Pons token, затем
записать ожидаемый token во все конструкторы. Нельзя заменить это произвольным
CREATE2 для C с immutable token: можно получить циклическую зависимость адресов.

План nonce обязателен на время первых CREATE; посторонняя транзакция кошелька
требует сверки/перепланирования оставшихся шагов. Схема предназначена сначала для
обычного EOA. Account abstraction/bundles и собственная factory — отдельная адаптация,
не предположение, что они прозрачно сохраняют инициатора Pons.

Контракты должны принимать ожидаемый ещё не созданный token, но до активации
проверять реальные роли и связи. Только заранее определённый инициатор/проверяемый
plan может закончить связывание. Нельзя оставлять публичный неограниченный initialize.

Ориентир: 3 CREATE + launch + 1–2 activation/bind calls, то есть 5–6 tx без покупки;
с USDG opening buy может добавиться approve. Это оценка предложенной архитектуры,
не обещание числа подписей: policy source, RNG wiring и финальный дизайн изменят граф.

## Восстановление

Сохраняем planId/hash, chain/account, salt, metadata hash, expected addresses,
версию/параметры модулей, профиль внешнего кода, nonce каждого шага, tx hash и receipt.
Wallet rejection оставляет шаг подготовленным. После неизвестного результата
сначала сверяем известный hash, nonce, ожидаемый runtime и события; без доказательства
не отправляем повторно и не меняем salt. Replacement проверяется по содержимому.

Если токен создан, а activation прерван — показываем «токен торгуется, программа
донастраивается», продолжаем тот же граф. Индексатор догоняет с launch block, а
комиссии могут накапливаться в escrow; draw до допуска запрещён. При reorg ждём
подтверждения и пересобираем допустимую историю, не меняем раскрытый результат.

Изменение Pons economics может изменить предсказанный token. Если наши контракты
уже привязаны к прежнему expected token, нельзя молча обновить pin и продолжить.
Нужен новый просмотр плана и отдельное решение о неиспользуемых контрактах/расходах.
Смена metadata или account после начала deployment также не обычное редактирование формы.

## Минимальные проверки будущей реализации

1. Два экземпляра: разные средства, snapshots, RNG domain, журналы и ошибки.
2. Прерывание после каждого шага: продолжение без дублирования CREATE/launch.
3. Drift nonce/economics/code/recipient: остановка до новой подписи.
4. Самая ранняя покупка в launch block: корректные билеты и остаток.
5. Atomic opening buy: success, недостаточный allowance, slippage revert, refund,
   корректная атрибуция payer и recipient. Никакого fallback minOut=0.
6. Curve sweep, pool quote-only sweep, ожидание Pons operator, частичный claim.
7. Повторный pull/transfer: отсутствие двойного учёта; постороннее пополнение согласно правилам.
8. Неудачный новый сбор не блокирует уже начисленные выплаты.

## Решения до финансового кода

Короткое предложение владельцу отправлено в диалоге, ответ пока не зафиксирован:
встроенные Holders/Buyback выключены, полученные creator fees идут в нашу программу,
обычного пользовательского метода вывода будущего потока из неё нет.
Это не устраняет внешние права протокола Pons: их надо раскрывать отдельно.

Ещё открыты: точка отсчёта первого/следующих интервалов, пустой набор, округление,
изменяемость параметров и адреса команды, gas budget и посторонние пополнения.
Предложения — [PRODUCT_SPEC](PRODUCT_SPEC.md). Переходим к локальным финансовым
контрактам после согласования правил; исследовательские неизвестности Holders
не блокируют собственный шаблон, который не использует Holders.
