# Отложенное распознавание покупок

Решение владельца 12.10.2026: применять механику QIANQI ко всем новым токенам
платформы. Покупку сначала сохраняем, проверенный маршрут даёт начисление,
неизвестный остаётся в очереди. Полное покрытие маршрутов не является условием
запуска. Новые маршруты добавляются после исследования и проверки, не автоматически.

Реализация локальная, исходная точка c50337a. Production и исходный QIANQI
не менялись; публичных отправок нет. Это дополнение и исправление границ
[первого пакета IGW](IGW_ROUTES_WALLET.md).

## Общие правила

1. Scanner сохраняет finalized receipt, transaction и привязку к блоку.
   Каждый `CurveBuy` кривой конкретного токена становится `WAITING_RECOGNITION`.
   Обнаружение не обращается к trace RPC и не зависит от знания маршрута.
2. Исходное наблюдение неизменно. Указанные в нём sender/recipient — связи
   с адресами для поиска, а не доказанный плательщик или право на билеты.
   Сумма и получатель билетов появляются только после проверки.
3. Отдельный курсор распознавания обходит очередь небольшими порциями:
   до 16 наблюдений и одной трассировки за проход; повторная попытка через минуту.
   Нераспознанная покупка не мешает следующей покупке и не запрещает розыгрыш.
   Недоступный trace RPC оставляет покупку в очереди.
4. Проверенное свидетельство включается в `draw-recognition-v2` bundle:
   policy hash, IDs покупок, версия проверяющего адаптера, контекст исполнения.
   Перед подписью свидетельство проверяется снова. Подтверждение bundle
   регистрируется существующим PurchaseRecognition контрактом.
5. Начисление происходит по блоку finalized-подтверждения, не задним числом
   по блоку покупки. Уже замороженные/завершённые розыгрыши неизменны;
   поздние билеты доступны будущим розыгрышам. Пока отправленное подтверждение
   не finalized и не проиндексировано, сохраняется прежний finality guard.
6. Candidate ID не начисляется дважды. Повторное чтение использует свидетельство
   из подтверждённого bundle, а не изменяемую очередь. Остаток до следующего
   билета накапливается по прежним правилам токена.

Порог, распределение денег, Short/Monthly, RNG, кошельки и журналы не объединяются.
Очередь находится в ledger конкретного проекта под существующей PostgreSQL lease/RLS.
Общие только код и проверенные версии адаптеров. Bundle другого policy не принимается.

## Версии и эксплуатация

Новые owner-launch-v2 получают `purchaseAccounting: deferred-purchases-v1`
в неизменяемой identity запуска и policy независимо от выбранного Short/Monthly.
Сохранённые запуски без этого поля продолжают прежний путь: скрытой миграции нет.
Для IGW новый owner journal ещё предстоит создать; перед подписями проверить поле.

Реестр находится в `src/tickets/deferred-recognition.mjs`. Начальные версии:

- `direct-curve-opening-v1`: direct USDG и opening buy;
- `pons-router-65050-20261012-v1`: проверенные USDG/native пути текущего 0x65050;
- `pons-usdg-self-batch-v1`: проверенный USDG self-batch.

Добавление маршрута: сохранить исходные наблюдения и публичные свидетельства,
написать ограниченный verifier и отрицательные тесты, добавить новый ID в реестр,
проверить повторную обработку старой очереди. Старые версии verifier сохраняются
для воспроизведения подтверждённых начислений. Изменение уже опубликованной версии
под тем же ID недопустимо. Исполняемый код и суммы из внешнего JSON не принимаются.

Runtime v2 поддерживает общий необязательный `recognitionAdapters` — список
разрешённых ID из встроенного реестра. По умолчанию включены все проверенные версии;
`[]` оставляет обнаружение и существующие розыгрыши, но не готовит новые начисления.
Изменение списка снимает минутную задержку старых попыток. Policy hash токенов
при расширении списка не меняется; подтверждённые bundles воспроизводятся даже
при отключении соответствующего адаптера для новых начислений.

Батч подтверждения — до 50 покупок с ограничением размера доказательств.
Слишком большое свидетельство остаётся в очереди; расширение лимитов требует
отдельной проверки. Архивный RPC должен возвращать исходные блоки/code;
trace RPC требуется только соответствующим адаптерам. Его недоступность при
старте не блокирует обычное чтение: сеть проверяется перед каждой трассировкой.
Неверная сеть или ошибка оставляют покупку без начисления. Трасса — свидетельство
доверенного RPC, не криптографическое доказательство исполнения.

## Кабинет и границы покрытия

Общий счётчик показывает число покупок в ожидании. Личный endpoint выдаёт
для запрошенного адреса количество и до 20 ссылок на связанные покупки,
отдельно от подтверждённых билетов. Непроверенные суммы не показываются.
Связь по sender/recipient не обещает начисление этому адресу. Общий API не
выдаёт карту кошельков или исходные свидетельства.

Текущее обнаружение — события `CurveBuy` закреплённой кривой Pons.
Неизвестный агрегатор с таким событием сохраняется для будущего распознавания.
Продажа и обычный перевод не считаются покупкой. Торговля после graduation
на DEX требует отдельного источника событий и адаптера; этот пакет её не добавляет.
Проверяющие адаптеры сейчас поддерживают одну покупку в транзакции;
множественные/неоднозначные операции сохраняются, но не начисляются без расширения.
