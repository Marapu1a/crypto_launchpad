# Учёт покупок по данным Pons

Решение владельца 13.10.2026: Pons — доверенный источник покупок, платный RPC
для их обнаружения/трассировки не используется. Наше обязательство — прозрачный,
воспроизводимый расчёт и отсутствие дублей. Это меняет границу доверия прежней
архитектуры; независимое доказательство полноты блокчейна здесь не заявляется.

## Реализованный пакет

[Сборщик](../scripts/pons-accounting/accounting.py), Python stdlib + SQLite.
Локальный отдельный журнал; текущий финансовый worker и production ledger не
подключены. Рабочее дерево поверх e3585b6, проверка API 13–14.10.2026, UTC/МСК.
Никаких RPC, секретов, подписи, отправки или изменения старых frozen snapshots.

- GET `/api/launches/{token}` сверяет token, quote address/decimals, stage,
  tradeCount и lastTradeAt. Неизвестный stage останавливает сбор для проверки.
- GET `/api/launches/{token}?view=trades`, затем opaque nextCursor. Прочитанная
  история сверяется с tradeCount и повторной metadata. На изменившейся истории,
  ошибке сети или лимите страниц старый успешный журнал сохраняется.
- ID `txHash:logIndex`, project + immutable profile, полный исходный ответ каждой
  страницы, исходные строки и нормализованные действия сохраняются в SQLite.
- BUY: trader Pons, quoteAmount Pons, целочисленное суммирование в единицах quote,
  перенос остатка. SELL не отнимает билеты. Нет ограничения первым часом токена.
- Decimals JSON читаются как строки, не float. Непредставимые дроби/NaN/отрицательные
  значения не округляются, а останавливают проход. Сеть этих экземпляров — 4663;
  профиль/ссылки этой реализации не универсальны для других сетей.
- Список исключённых адресов явный в profile; скрытого исключения любого trader нет.
  В локальных сравнениях исключены deployer, curve, factory, fee collector и
  известный router. Только venue=curve проверен. Иные BUY остаются review-required.
- Изменение/исчезновение старой сделки создаёт review; начисления не переписываются.
  Автоматического разрешения review пока нет. После восстановления ответа review
  не снимается сам. Существующие данные доступны вместе со статусом ошибки.
- Один writer на SQLite обеспечен OS file lock, освобождаемым при выходе процесса.
- JSON/HTML отчёт: кошелёк, сумма, действие, новые билеты, остаток, ссылка на tx.
  Сортировка timestamp/txHash/logIndex детерминированная; порядок разных tx с одной
  секундой не заявляется точным порядком исполнения блокчейна. Итог суммы неизменен.

## Экономия и восстановление

При неизменившихся metadata — один HTTP GET на проект за проход. Это оперативная
подсказка от Pons, не доказательство отсутствия исправлений старых сделок.
Каждые 6 часов либо --force — полный обход для проверки исправлений/удалений.
При новой торговле тоже полный обход. Для двух небольших историй это 3/5 запросов;
для активного будущего токена нужна инкрементальная пагинация, ещё не реализована.

По умолчанию максимум 20 страниц за проход. Упёрлись в лимит — unavailable,
не частично готовый ledger. После прерывания обход начинается заново с первой
страницы, старое начисление остаётся; persisted resume cursor ещё не реализован.
Таким образом текущий пакет пригоден для малых историй и сравнения, не для
неограниченно активного проекта. --watch: 5 минут, при ошибках backoff до часа.
Сбор относится только к покупкам; фонд/финальные выплаты этим API не проверяются.

## Проверенные реальные данные

Источники: публичный Pons API и сохранённые ответы в
`.local/pons-accounting/research/`; результаты в `.local/pons-accounting/reports/`.

| Проект | Все сделки | BUY / SELL | BUY кошельков | Порог сравнения | Всего начислений |
|---|---:|---:|---:|---:|---:|
| IGW | 18 | 6 / 12 | 5 | 10 USDG | 38 |
| QIANQI | 126 | 70 / 56 | 50 | 100 USDG | 27 |

Это накопленные начисления по новой базе суммы, НЕ текущие доступные билеты:
потребление предыдущими розыгрышами и существующие credits не мигрированы.
Порог QIANQI взят из сохранённого проверенного профиля/fixtures; live policy
сервера в этом пакете не перечитывалась. IGW — из IGW_LAUNCH_PROFILE.
После перезапуска повторный проход дал по одному запросу, новых начислений нет.

Сверка исторических fixtures QIANQI с Pons:
- tx `0xeb4228dbc60761390d905d8570c82ae8614ba962519cc30c51d67a2f0fb47ba0`:
  Pons trader совпал с получателем; quoteAmount=198 USDG. Старый wallet-net-debit
  был 200 USDG с комиссией; при пороге 100 это 1 вместо 2 билетов и остаток 98.
- tx `0xb64952128bacef2516f47eca910eab4c324f032ef115a41315a21d4bda500c79`:
  trader совпал, сумма 93.087934 USDG совпала с полученной curve.

Проверка двух примеров не доказывает семантику всех маршрутов. В QIANQI 70 BUY
нет trader=известный router; у IGW router встречается среди SELL. Refund-сценарий
и сделки после graduation не проверены. В Pons trade record отсутствуют отдельные
поля возврата и blockHash. Не выводить их из догадок и не называть API finalized.

## Запуск и тесты

Локальные профили экземпляров не содержат ключей:

```powershell
python scripts/pons-accounting/accounting.py --profiles .local/pons-accounting/profiles.json
python scripts/pons-accounting/accounting.py --profiles .local/pons-accounting/profiles.json --watch
python scripts/pons-accounting/test_accounting.py
```

12 тестов PASS: накопление/остаток/продажа, idempotency после открытия БД,
network recovery, corrections/deletion, pagination overlap/loop/budget, count mismatch,
mid-page failure и racing metadata, decimal precision, profile/lock, unknown venue
после ошибки и межпроектная изоляция. RPC не входит в интерфейс сборщика вообще.

## До подключения к розыгрышам

Следующий локальный пакет — [интеграция исполнителя и сравнение миграции](PONS_WORKER_REHEARSAL.md).
Он сохраняет прежние подтверждённые credits: QIANQI после такого переноса имеет
28 начисленных билетов, а не 27 чистого пересчёта Pons. Production не переключён.

Нужны явная версия policy и граница миграции, импорт consumed/frozen данных обоих
проектов, адаптер участника в financial worker и public API. Новое накопление не
может просто заменить старый gross ledger. Финальность draw/журнал nonce/деньги
сохраняются отдельным слоем бесплатного RPC. После новых тестов — отдельный release.
Следующий пакет: выполнить это подключение на копиях, проверить цикл без trace,
затем согласовать production-переключение. QuickNode остаётся отключённым.
