# Новый токен: UI → Pons → общий backend

10.10.2026, пакет после `fb3ccba`. Это сквозной **локальный** запуск нового проекта,
не переключение QIANQI и не допуск контрактов Local* в сеть 4663.

## Как посмотреть

```text
npm run build
npm run studio
```

Адрес панели: http://127.0.0.1:4185/launch.html. На момент отчёта отдельный стенд
оставлен работающим в фоне; указатель `.local/studio/current.json`.
Остановка: `npm run studio:stop` — завершает только этот стенд, файлы сохраняет.
Нужен локальный PostgreSQL (`PG_BIN`, по умолчанию Windows PostgreSQL/17/bin)
и уже настроенный archive RPC. Создаются собственные PostgreSQL cluster/database
и Hardhat fork 31337 на отдельном свободном порту, исторический блок 82000000.
Пути/credentials production и QIANQI не используются.

В панели можно открыть существующий проект, создать новый черновик и запустить
его. После запуска поля фиксируются; повтор продолжает прежний ID/salt/журнал.
Кнопка «Проверить покупку и розыгрыш» выполняет **одну** тестовую покупку 3119 USDG
и переводит исторические часы к настоящему времени. Повтор этой кнопки не
создаёт следующую покупку. Затем worker работает сам, включая ожидание drand.
Это специальная функция репетиции, а не часть реального продукта.

Состояние покупки/создания сохранено на диске, финансового worker и билетов —
в PostgreSQL. Перезапуск только панели сохраняет fork и БД:
`node scripts/run-studio.mjs <runtime.json>` из указателя выше. Старую панель
предварительно остановить. Полная остановка стенда завершает непостоянную цепочку;
новый fork имеет другой instanceId и не может продолжать старые журналы.
Для новой быстрой репетиции создаётся отдельный стенд; старые файлы не удаляются.
После перевода общей копии цепочки в настоящее время новый контракт начинает
свои первые 24 часа заново; кнопка не переводит его в будущее ради обхода drand.

## Что соединено

1. Форма TOKEN/USDG с preset 2% creator fee, 80/15/5, билет за10 USDG,
   Short раз в86400 секунд от settle, фонд от50 USDG, один слот. Настройки
   валидируются и на клиенте, и на сервере; доли/порог/интервал/корзина гибкие.
   Недостающие веса призов заполняются единицами; до64 мест. Monthly выключен;
   этот шаблон отклоняет его включение. Гарантии победителя нет.
2. До deploy читаются и проверяются условия Pons и баланс. Затем создаются
   LocalDrandShortProgram, splitter, collector и recognition source. Комиссии
   направляются в collector; произвольная подмена fee wallet исключена.
3. Approve → защищённая симуляция Pons launch → launch → bind. Deploy и запуск
   имеют durable signed journal: raw/hash/nonce записываются до broadcast.
   После сбоя продолжается та же подпись; изменение запроса/шаблона/instance,
   потеря lease, занятой nonce и reorg блокируют продолжение.
4. Регистрация project/module/domain/source, финансового executor и ledger
   существующими PostgreSQL-компонентами. Частичная регистрация повторяема.
   Если БД помнит проект, но launch journal потерян, создание с нуля запрещено.
5. Общий процесс обслуживает проекты по очереди; у каждого отдельные contracts,
   executor, state, bundles, tickets, RNG и финансовые операции. Ошибка одного
   проекта фиксируется как blocked и не прекращает обход соседей.
6. Прямые распознанные покупки перепроверяются по chain receipts и публикуются
   через recognition source. Ledger начисляет по confirmation block; старый
   frozen snapshot не изменяется. Неизвестные маршруты остаются неподтверждёнными,
   а не превращаются в билеты. Их отдельные адаптеры в этот пакет не включены.
7. На `slug.localhost:4185` работает общий шаблон сайта. Host определяет проект
   через прежний shared API/RLS; неизвестный Host отклоняется. В панели показаны
   фонд, цикл, назначенные/выплаченные призы по событиям контракта.

Основные файлы: `server/studio/`, `src/studio.mjs`, `src/project.mjs`,
`scripts/start-studio.mjs`, `scripts/run-studio.mjs`. Native QIANQI adapter,
vendor, исходный rh_project и production не менялись. Миграций БД не добавляли.

## Границы и следующий пакет

Полный UI-путь работает на стенде. **Не готовность реального запуска:**

| Область | Состояние / необходимое действие |
| --- | --- |
| Сеть | Все Local* контракты и guards ограничены31337. Нужен отдельно проверенный production template для4663, clock/finality/admission, gas policy и signer custody; удалять local guard недостаточно. |
| Кошелёк | Публичный известный Hardhat deployer и отдельные generated test executors. Реальную подпись владельца и onboarding production worker подключить отдельно. |
| IPFS | Поле готового URI, тестовый CID в preset. Upload/pinning и проверка доступности ещё не подключены. |
| Pons | Проверен исторический fork82000000. Перед реальным deploy заново читать актуальные economics/runtime, graduation и поддерживаемые маршруты. |
| Сайты | Общий локальный шаблон/Host routing. DNS, TLS, production поддомены и публичная страница розыгрышей — следующий этап. |
| Общий backend | Общая реализация/кластер стенда, роли и изолированные project IDs. До production отдельное подключение, не автоматическое использование БД QIANQI. Raw chain source пока отдельный на проект; объединение чтений — отдельная оптимизация. |
| Доступ | Только loopback и local Host, same-origin JSON writes. В provisioning-процессе есть local DB admin. Это не публичная административная API; до публикации нужны authentication и отдельные provisioning права. |

Следующий предлагаемый пакет — production-профиль первого USDG/Short шаблона:
сопоставить его контрактные/финансовые пути с рабочим QIANQI, закрыть production
clock/finality и signer lifecycle, затем кошелёк/IPFS и отдельная репетиция
точных production artifacts. До этого настоящие deploy/переводы не делать.
