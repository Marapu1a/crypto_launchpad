# Репетиция production Short на настоящем Pons

10.10.2026, пакет после `605e1c4`. Использованы прежние production artifacts и
PostgreSQL worker на отдельном историческом fork. Подключена проверка пакетных
USDG-покупок кошелька. Исходный QIANQI, сервер, production БД и публичные
транзакции не затронуты.

## Стенд и источник

`npm run test:production-fork` запускает in-process Hardhat с chain ID 4663,
fork блока **82000000**, hash
`0x4d5490ff919a301834746f8d6a8c6b5fe532207954eadf34a84823fdca85d549`.
Внешний RPC используется движком fork только для чтения состояния; сетевого
signer или публичного network configuration в harness нет. До любых отправок
проверяется Hardhat metadata, исходная сеть, блок и runtime фабрики.

Pons factory/router/curve, USDG, escrow и batch executor — настоящие контракты
из этого среза. Тестовые счета получают USDG через impersonation escrow только
в локальной копии. Наши контракты разворачиваются из неизменной сборки:
`0x24fe240da110404159ec3b3695b4b4c1dd6a312f4dabf60e261f7880207c9ad1`.
Конструкторы, chain guard 4663 и BLS verifier не заменялись заглушками.

Hardhat исполняет EIP-7702 под Prague, artifacts скомпилированы для Cancun.
Это тест совместимости этих операций, не полная эмуляция консенсуса Orbit.
Время и finalized observer моделируются. Два настоящих исторических drand
beacon сохраняются в каждом отчёте: первый для readiness, второй для выбранного
раунда. Его логическое время наступает после freeze; подпись уже известна
тестовому harness. Это не доказательство непредсказуемости будущего live-раунда.

## Проверенный путь

1. `preparePlan` → approve → две симуляции → launchAndBuy: создан TOKEN/USDG
   со стартовой покупкой 5 USDG и creator fee 2%. Адреса совпали с симуляцией.
   Fee recipient — наш collector, bindings проверены перед регистрацией worker.
2. Прямые покупки на 3119 и 10 USDG. Пакетные покупки по 10 USDG: одна с новой
   EIP-7702 авторизацией, другая через делегацию, установленную ранее.
3. Worker собрал escrow, перечислил доход splitter и доставил 80/15/5.
   Отдельный publisher подтвердил пять покупок; появились 312/1/2 билета у
   трёх разных участников. У первого осталось 4 USDG до следующего билета.
4. После интервала 24 часа worker зафиксировал фонд, dataset и checkpoint,
   запросил один раунд, проверил BLS, доставил seed и выполнил settle.
   Результат независимо сверяется с JS `compute` по фактическому контексту.
5. Покупка 10 USDG после freeze не изменила snapshot. После settle у этого
   участника остался ровно следующий билет 2..2. Повторные passes не платят дважды.

## Фактические комиссии на этом срезе

Base fee **1%**, creator fee **2%**, protocolFeeShareBps **3000**. В этом Pons
получатель creator fees также получает остаток базовой комиссии после доли
протокола. Поэтому нельзя считать наш доход как `объём × 2%`.

Для первых пяти покупок общий объём 3154 USDG:

| Проводка | USDG |
| --- | ---: |
| Базовая комиссия | 31.54 |
| Creator fee | 63.08 |
| Протокол: 30% базовой комиссии | 9.462 |
| Наш collector: creator fee + остаток base fee | **85.158** |
| Призовой фонд: 80% фактического дохода | **68.1264** |
| Команда: 15% | 12.7737 |
| Операционная доля: 5% | 4.2579 |

Это результат **исторического блока**, не утверждение о неизменности текущих
условий Pons. Перед реальным запуском нужны свежие on-chain параметры.
Worker делит реально полученные средства; бизнес-настройки 2% и 80/15/5
не менялись. Операционная доля остаётся USDG, автоматической конвертации в gas нет.

## Пакетные покупки и ограничения

`production-recognition.mjs` использует уже перенесённый чистый verifier QIANQI
`src/qianqi/routes/ordinary-batch.cjs`, без его runtime/ключей/настроек.
Профиль нового токена явно закрепляет batch executor:
`0x63c0c19a282a1b52b07dd5a65b58948a07dae32b`, runtime hash
`0xa06befcb6f1d7b6c566a607d9d5d932f9b267f3470e55940225c6ee9c4c5e6b0`.
Отсутствие pin сохраняет прежнее поведение: неизвестному маршруту билеты не выдаются.

- Допускается только точная последовательность USDG approve + curve buy,
  self-call с нулевым native value и совпадающим плательщиком/получателем.
- Проверяются оригинальные calldata, receipt, переводы и события. Shape match
  отдельно от подтверждения исполнения сам по себе не даёт права на билет.
- Для type 4 проверяются signer авторизации, chain 4663 и nonce.
- Для type 2 нужна делегация на закреплённый executor **в родительском блоке**.
  Изменение авторизации этого аккаунта внутри блока запрещает такое признание.
- Runtime executor проверяется в родительском и текущем блоках. Контекст
  сохраняется вместе с исходными evidence и повторно проверяется при credit.
- Native-funded self-batch, агрегаторы, relayers, pool/graduation не включены
  этим пакетом. Для них остаются неподтверждённые события и отдельные adapters.

Розыгрыш и publisher по-прежнему используют finalized cutoff. Поздний credit
не переписывает прошлые snapshots. Наличие билета не гарантирует победу.

## Результаты и продолжение

6 сквозных fork-сценариев PASS:
`.local/test-results/production-pons-fork-2026-10-10T09-59-16-559Z/report.json`.
В нём source hashes, исходный fork block/hash, фактические суммы, snapshot,
раунд и resultHash. Рядом — policy с runtime pins и два beacon. Ранний
успешный прогон `09-56-02-365Z` сохранён отдельно; окончательным является
прогон с source hashes и предварительным gate reviewed batch executor.

3 новых unit-сценария PASS: правильная/поддельная авторизация и chain/nonce,
родительская делегация/её изменение внутри блока/runtime drift,
подмена платежа/чужой токен/отсутствие pin. 8 соседних ticket-тестов PASS.
6 соседних двухпроектных worker-сценариев PASS после изменения общего ledger:
`.local/test-results/production-worker-2026-10-10T09-59-26-731Z/report.json`.
Проверены старые профили без batch pin, финансовая изоляция, потеря DB session,
поздняя финальность и отсутствие повторной выплаты. Всего 23 сценария PASS.

В итоговом fork-прогоне выплачено 68.1264 тестовых USDG, liabilities=0.
Раунд 21368427, resultHash
`0xc1914cfb229fd149ace254900feb82ac1d8376eb03a6cf2af4ef0522fb075c21`.
Это результат тестового набора, а не гарантия победителя для будущего токена.

Ранние неуспешные снимки сохранены: Hardhat требовал локальный блок поверх
fork перед историческим eth_call; BrowserProvider не выбирает impersonated
адрес через getSigner, поэтому локальное тестовое пополнение выполняется
через eth_sendTransaction. Это исправления harness, не изменения Pons.
Unit fixture дополнен настоящим полем yParity подписи вместо сериализации
только v; production verifier не ослаблялся.

Далее — кошелёк владельца и IPFS в форме запуска: публикация выбранной картинки,
подпись точного проверенного launch plan и восстановление процесса. После этого
подключение нового проекта к постоянному runtime, общей загрузке блоков,
проекциям API и сайту на поддомене; явные production timing bounds и отдельное
решение о первом публичном запуске. Успешный fork не включает эти шаги автоматически.
