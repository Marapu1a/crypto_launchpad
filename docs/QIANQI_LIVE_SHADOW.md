# QIANQI: обновляемый shadow с курсором PostgreSQL

09.10.2026, пакет поверх f7e460c. Read-only blockchain/API; изменения только в локальном проекте и изолированных тестовых БД. Старый QIANQI worker и сервер не переключались.

## Новый путь

advanceShadow читает только новые CurveBuy/CurveSell, confirmations и lifecycle-события после сохранённого head. Начальная точка — перепроверенный qianqi_imports. Проверяются прежний canonical hash, неизменный профиль, finalized новый API head, runtime/bindings/reserves и единая генерация страниц API. Повтор того же head ничего не записывает.

Прямые и self-batch покупки используют прежний verifier. Неизвестные внешние маршруты остаются WAITING_RECOGNITION. Self-batch, не прошедший проверку текущего decoder/authority/runtime, останавливает цикл и требует отдельного разбора маршрута; автоматического обхода этой проверки нет. Поздние покупки допускаются только после проверки bundle/source, original receipt/calldata/trace/runtime, с первым creditedAt; повтор не переносит дату начисления. Новые Short snapshots проверяются общим dataset verifier. Monthly freeze, pool activity/graduation и смена политик пока останавливают этот adapter.

Балансы сравниваются для всех известных плательщиков и отправителей ожидающих покупок, включая кошельки вне прежнего late cohort. Старые snapshot hash не должны меняться. API здесь — объект сравнения и указатель высоты, не источник сумм для начисления. Пропущенные RPC-события по-прежнему не исключены независимым consensus proof.

Это инкрементальная выборка событий, но **не полностью инкрементальные расчёты/хранение**: текущие покупки и lifecycle пересчитываются в памяти, а в БД сохраняется полный проверенный payload на каждый новый head. Для нынешнего размера QIANQI этого достаточно для репетиции; перед длительной эксплуатацией нужно оценить рост и перейти к дельтам/ограниченной истории наблюдений. Raw receipts повторно читаются только для новых событий и необходимых поздних proofs; новый snapshot может потребовать чтения dataset history.

## Курсор и отказы

Миграция008: qianqi_live_heads с previous_digest, digest, head и payload; qianqi_live_halts с причиной остановки. Исходный импорт не изменяется. FORCE RLS, composite FK project/module, runtime SELECT/INSERT без UPDATE/DELETE. API и финансовый executor новых прав не получают.

Новый head и результат сравнения фиксируются одной транзакцией с advisory lock и проверкой прежнего digest. Два наблюдателя не создают дубликат; устаревший результат требует повтора. Контекст общей lp_jobs остаётся доверенной границей, не защитой от компрометации credentials.

RPC/API-сбой, неподдерживаемое событие, смена API generation и несовпадение балансов оставляют предыдущий cursor. Изменение canonical hash дополнительно создаёт durable halt: автоматический повтор после перезапуска запрещён. Для восстановления нужна отдельная проверка ветки, автоматического rollback нет.

## Запуск

Сначала нужен верифицированный исторический импорт и migration008. Переменные SHARED_JOBS_URL, SHARED_PROJECT_ID, SHARED_MODULE_ID задаются локально; URL БД и RPC в отчёты не записываются.

- node scripts/qianqi-live-worker.mjs — один цикл с PostgreSQL.
- node scripts/qianqi-live-worker.mjs --watch — повтор каждые60секунд после завершения цикла; SIGINT/SIGTERM прекращает после текущего цикла. Reorg/halt завершает наблюдение.
- node scripts/qianqi-live-shadow.mjs — автономный capture от первоначального verified archive без записи БД.
- npm run test:shared:qianqi-live — изолированная БД, импорт и проверки live cursor/restore.
- node tests/qianqi/live.mjs — captured evidence и историческая покупка.

Цикл ограничен пятью минутами/2000RPC; catch-up до1млн блоков, getLogs чанками90000. При большем отставании нужна отдельная процедура catch-up, курсор не перескакивает.

Серверный service/автозапуск этим пакетом не устанавливался. Watch mode подготовлен; непрерывный длительный production-прогон не заявляется. Текущий live shadow сверяет билеты и inventory, но не выполняет повторный полный RNG/финансовый аудит каждого нового розыгрыша.

## Проверка и результат

Проверки: **21 интеграционный сценарий PASS**, затем отдельная успешная перепроверка dump/restore (исходный тест сравнивал строки без полного ORDER BY; исправлен). 8 live evidence, 8 history evidence и19 unit PASS. Отчёты: .local/test-results/shared-2026-10-09T16-02-50-794Z/report.json (сохранён исходный FAIL сортировки), .local/test-results/shared-2026-10-09T16-02-50-794Z/restore-and-live-recheck.json (PASS восстановления и двух запусков с живыми RPC/API). Первый реальный процесс записал head84275104, второй вернул UNCHANGED без дублей. Сам двухцикловый процесс не оставлен работать в фоне. Исторический исходный head84135771; первый live capture .local/test-results/qianqi-live-2026-10-09T15-59-42-447Z/report.json достиг84271425 (hash0x49b51cb07844a3f11e13a5e91a244d55ba3cc81212801adef514ec7bf43eb386). Сверены53 адреса:52 кошелька с допущенными покупками и ещё один отправитель двух ожидающих распознавания покупок. Новых событий BUY/SELL/recognition/lifecycle в этом диапазоне не было. Это не доказательство полного покрытия будущих маршрутов.

Далее: независимый пересчёт Short outcome из seed/участников/правил, затем обследование сервера и отдельная репетиция эксплуатации с проектными правами исполнителей. Handoff QIANQI требует актуальной сверки on-chain и приватного операционного состояния по отдельному разрешённому пакету; два финансовых worker одновременно не запускаются.
