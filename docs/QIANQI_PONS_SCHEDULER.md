# QIANQI: локальный цикл из журнала Pons

14.10.2026 МСК, рабочее дерево поверх e3585b6. Продолжение
[переноса учёта](QIANQI_PONS_MIGRATION.md). Службы VPS остаются остановлены;
QuickNode, ключи и production-журналы не использовались. Публично получен только
исторический drand beacon 9336626; его подпись проверяется реальным адаптером
на локальной цепочке. Повторный тест использует сохранённый fixture без сети.

## Реализация

[Новый планировщик](../server/adapters/qianqi/pons-scheduler.mjs) — внутренний
Hardhat-only entrypoint, отдельный от production run-pons-public. Он использует
прежние Short/Monthly executors и формат jobs, а покупки получает через
loadReport из проверяемого журнала Pons. HTTP/config-переключателя пока нет.
Он требует chain4663, совпадающий локальный Hardhat instance, loopback RPC,
исходный domain и каноническую границу переноса. Это стендовая защита от случайного
подключения, не гарантия против намеренно поддельного provider.

Порядок прохода:

1. Под файловой блокировкой восстановить pending-транзакцию, затем обработать
   lastResolved. При отсутствии квитанции/финальности ждать, не заменять отправку.
2. Сверить текущие epoch/pending/lastTerminal контроллеров с журналом. Неизвестное
   изменение останавливает новые действия до получения конкретных квитанций.
3. При pending draw вызвать прежний drand worker с отдельным журналом;
   обработать уже начисленные награды через прежний claim фиксированному получателю.
4. Принять свежий отчёт Pons. Ошибка источника запрещает новые jobs, но не стирает
   сохранённые наборы и не мешает завершать существующие обязательства.
5. Сохранить artifact/job до первой отправки; закрепить cutoff, выполнить один
   шаг прежнего исполнителя. Short/Monthly чередуются. За проход drand может
   выполнить несколько собственных действий по своему журналу.

Состояние миграции и jobs сохраняются одним атомарным файлом через существующий
withState. Транзакционная граница сохраняет intent/hash/receipt до изменения
учёта. При сбое после сохранения receipt повторный проход применяет его ровно
один раз. Неизвестный hash после сбоя между intent и отправкой остаётся blocked;
автоматического угадывания nonce или повторного платежа нет.

[Обработчик квитанций](../server/adapters/qianqi/pons-controller-events.mjs)
принимает события только связанных Short/Monthly/vault:

- AttemptsFrozen сверяется с сохранённым artifact, резервирует именно его диапазон.
- AttemptsConsumed списывает только замороженный диапазон; поздние покупки остаются.
- RewardAssigned/RewardPaid образуют очередь выплат и подтверждение оплаты.
- Объявление/активация правил и закрытие пустой эпохи обновляют эпохи по событиям.
  Пропущенную границу нельзя молча применить задним числом к уже принятым покупкам.

События упорядочены по block/transaction/log, повторная квитанция идемпотентна,
изменившаяся ранее принятая квитанция отклоняется. Исторические draws/rewards
сохраняются, новые выплаты хранятся отдельно в controllerRewards.

## Запросы и границы автономности

Для собственных действий используется известный tx hash: квитанция и проверка
блока. Ни trace, ни сканирование BUY-событий, ни обход пустых блоков для покупок
не вызываются. Прежний исполнитель всё ещё проверяет публикацию chunks через
getLogs в диапазоне конкретного draw; контрактные чтения и finality тоже нужны.
Это не обещание нулевого RPC или уже доказанной бесплатной месячной квоты.

Сторонняя смена эпохи/выплата/операция выявляется сверкой состояния. Для неё нужно
передать receiptHashes; автоматический поиск неизвестных сторонних транзакций
не реализован. При неизвестном controller job или missingFrozenJob работа ждёт
явного восстановления. Импорт старых незавершённых transaction/jobs journals
в этот новый scheduler не выполняется. На сохранённом снимке QIANQI pending нет.

## Проверки

Контрактный стенд использует реальные прежние контроллеры, vault и drand adapter,
моделируемые покупки Pons, исторические подписанные beacon и локальную цепочку.
Проверяется полный цикл обоих видов, аварии после broadcast и сохранения receipt,
перезапуск без повторной выплаты, поздняя покупка и переход эпох.
Изначальные 4 билета каждого вида расходуются, поздний пятый остаётся открытым.
Последний прогон PASS: 6 сценариев внутри одного контрактного теста,
`.local/test-results/qianqi-pons-2026-10-14T07-25-42-336Z/report.json`.
18 unit tests и 12 lock/storage tests PASS. Первоначальный запуск lock-теста
из корня завершился MODULE_NOT_FOUND у дочернего процесса; запуск из штатного
runtime-каталога прошёл без изменения кода.
Офлайн-сверка сохранённого QIANQI также PASS:
`.local/pons-accounting/migration/rehearsal-2026-10-14T07-24-19-313Z/report.json`;
остатки Short 12 / Monthly 28 и два прежних draw сохранены.

Unit-проверки покрывают conservation/epochs/frozen, повторные/изменённые квитанции,
NO_WINNER, поздние покупки, запрет public provider. Смежный lock-тест запускается
из каталога runtime: его дочерний процесс использует относительный require.

```powershell
node --test tests/contracts/qianqi-pons-scheduler.test.mjs
node --test tests/unit/qianqi-pons-migration.test.mjs tests/unit/qianqi-economy.test.mjs tests/unit/pons-accounting.test.mjs
node scripts/rehearse-qianqi-pons.mjs
# cwd: server/adapters/qianqi/runtime
node --test test/local-state-lock.test.cjs
```
