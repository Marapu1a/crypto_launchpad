## Причина оставшейся ошибки QIANQI

Первоначальный инцидент — расход локального RPC-лимита во время обработки
комиссии и ожидания финальности. Позже возникла отдельная ошибка доступа:
`/var/lib/crypto-launchpad/pons-preflight/budget.json` принадлежал `root:root`,
mode 0600, при systemd User=`qianqi`. Последнее изменение файла было 15:22:06 UTC.

Причина второго сбоя — предыдущий диагностический запуск ассистента от root.
Хотя chain-запросы были только на чтение, общий RPC gate записывал расход и
атомарно заменил файл от имени root. Поэтому прежнее описание этой диагностики
как полностью read-only неточно: финансовые отправки не выполнялись, но файл
учёта RPC менялся. Ответственность за этот сбой — на диагностике.

Ограниченный повтор диагностики от сервисного пользователя показал `EACCES`
при чтении бюджета ещё **до отправки RPC**. Проверены checksum, config identity,
migration, DB role и executor binding; они совпали, stale state lock отсутствовал.

В ходе подготовки исправлен только владелец бюджета на `qianqi:qianqi`.
До/после chown байты совпали, SHA256:
`f5e5c56d5fb763c78ff2d64c97e87f630bebc45128d6e35b050a8c5e3c4c950d`.
Лимит, использованные запросы и начало окна не редактировались. Сервис не
перезапускался. После своей паузы он автоматически возобновил работу:
health в 16:35:43 UTC — QIANQI waiting, IGW service-sleep; permission error ушёл.
Это подтверждает устранение ошибки доступа, но старый код ещё способен расходовать
лимит на повторные полные проверки. Его заменяет подготовленный пакет.

Новый gate отказывает процессу с чужим effective UID **до замены файла**.
Ошибки ownership/permission/lock отображаются отдельными безопасными причинами
в health. Диагностику с общим RPC gate выполнять только от systemd User=qianqi.

## Установка и откат

На сервер подготовлены, **но не запускались с activate/rollback**:

```sh
python3 /opt/crypto-launchpad/deploy/pons-rpcfix-20261020-v4/manage.py --check
python3 /opt/crypto-launchpad/deploy/pons-rpcfix-20261020-v4/manage.py --activate
python3 /opt/crypto-launchpad/deploy/pons-rpcfix-20261020-v4/manage.py --rollback
```

`--check` читает файлы и systemd, проверяет обе сборки и текущий бюджет без RPC.
В 16:36 UTC: preflight-pass, 1400 запросов доступно, activationBudgetReady=true.
Это снимок, не резерв: старый worker продолжает работу и может расходовать лимит.
Установка повторно проверяет запас не менее 1000 запросов для холодного старта;
если его нет, нужно дождаться нового окна. Бюджет не сбрасывать и лимит не повышать.
Запас — операционная предосторожность, не гарантия расхода полного финансового цикла.

`--activate` проверяет точную старую версию и отсутствие постороннего override,
штатно останавливает только pons-runtime, проверяет уход процесса и lock-файлов,
устанавливает один drop-in `90-rpcfix-20261020.conf` с новыми WorkingDirectory,
ExecStart и проверкой нового manifest. Затем запускает runtime и ждёт свежий health.
Collector, API, monitor, конфиги токенов и ключи не переключаются.

Если старт нового unit не проходит, скрипт возвращает прежний код через rollback.
Если новый health требует внимания, состояние сохраняется и требуется разбор;
скрипт не пытается чинить финансовые журналы или повторять отправки самостоятельно.
После старта проверить оба проекта, свежесть публичных снимков и рост бюджета.
Ожидание финальности само по себе не является ошибкой и не требует отката.

`--rollback` принимает только свой drop-in с точным ожидаемым содержимым,
штатно останавливает runtime, проверяет lock-файлы, удаляет только этот override
и запускает прежний unit. Старые журналы/снимки/бюджет никогда не восстанавливаются
поверх новых: формат состояния не меняется, прежний код получает актуальные данные.
Откат не отменяет уже исполненные транзакции. Stale locks автоматически не удаляются.

При подготовке реальное переключение и реальный откат не репетировались на
работающем сервисе. Последующее разрешение владельца и отложенная активация
зафиксированы в разделе «Разрешённая выкатка и ожидание бюджета» выше.
