# PW: запуск через Pons и восстановление

19.10.2026 MSK (проверки 18.10 UTC), база `2b5d3d1` плюс рабочий пакет.
Новый coordinator проверен на локальном fork реальной сети Pons; production,
существующие IGW/QIANQI, ключи и реальные средства не изменялись.

## Что реализовано

`server/owner-launch/pw-coordinator.mjs` использует существующее хранилище
`owner_launches`, блокировку владельца, резервирование executor/publisher,
проверку истории receipts и финальности. Развёртывание включает девять шагов:

1. Managed holder vault.
2. Draw с механикой IGW и привязкой первого периода к запуску Pons.
3. Splitter 60/20/20.
4. Native collector.
5. Настоящий `launchToken` Pons: ETH, tax 3%, buyback off, collector как получатель.
6. Привязка collector к token/curve.
7. Привязка vault к splitter.
8. Привязка splitter к collector.
9. Привязка календаря draw к времени создания токена.

Адрес collector вычисляется по исходному nonce владельца. Он входит в параметры
CREATE2 токена Pons; затем рассчитанный token входит в scope/instance остальных
контрактов. Весь список запросов, nonce и адресов сохраняется до первой отправки.
Изменение входных данных не пересобирает начатый запуск под тем же ID.

Перед отправкой проверяются подпись, sender, сеть, nonce, calldata, value и лимиты
газа; signed bytes сохраняются в PostgreSQL. Coordinator сам не подписывает и не
отправляет транзакции. При потере ответа проверяется сохранённый hash, а не
создаётся новая транзакция. Пока результат неизвестен, следующий шаг заблокирован.
После сбоя процесса можно извлечь ровно те же bytes для отправки. Revert останавливает
запуск; автоматического изменения nonce или замены контрактов нет.

Каждый шаг перепроверяет предыдущие receipts, код развёрнутых контрактов, factory,
router, escrow, hook и mutable launchDeployer. После всех шагов проверяются связи
token/curve/collector/splitter/vault/draw и роли, затем ожидается finality. Завершение
deployment не регистрирует workers и не запускает денежное исполнение.

## Первый розыгрыш после настоящего запуска

`PwNativeShortProgram` наследует существующий native draw, не меняя исходный
контракт. До привязки к token розыгрыш закрыт. Разовая `bindLaunch` получает
`launchedAt` от curve, указанной в записи factory, и проверяет token, получателя
комиссий, native pair и выключенный buyback. Привязать может только deployer
нашего draw. После привязки отсчёт первых 30 дней начинается от этого времени;
следующие циклы используют прежний отсчёт от завершения предыдущего.

Это устраняет ошибку при долгом прерывании подготовки: контракт draw мог быть
создан за несколько дней до самого токена. В тесте между ними проходит 40 дней;
сразу после выпуска токена розыгрыш всё равно не готов. `launchAt` хранится
отдельно от изменяемого временем последнего завершённого цикла `lastTerminal`.

## Согласованный календарь холдеров

Владелец подтвердил: первый успешно принятый снимок после границы 30 дней,
с публикацией его точного времени; пропущенные периоды переносят средства без
восстановления исторических балансов. Профиль PW содержит
`holders.schedulePolicy = first-accepted-carry-v1`.

Для этой политики различаются:

- **Номер начисления** — последовательный 1, 2, 3, используется контрактом долга.
- **Календарный период** — 30-дневное окно от launchAt; его номер может перескочить.

Например, после первого начисления весь следующий период пропущен. В третьем
календарном периоде принимается свежий проверенный снимок и публикуется начисление
№2 из доступного фонда. Средства не расходуются на фиктивное начисление №2 за
прошлую дату. Старые долги сохраняются отдельно и не входят в свободный фонд.

Принятый снимок неизменяем: если публикация затем задержалась, продолжается тот
же расчёт, даже после следующей календарной границы. Заменять уже принятый список
новым нельзя. Preview возвращает `calendarPeriod`, `skippedCalendarPeriods` и
`acceptedSnapshotAt` (время проверенного блока). Это поля backend, не утверждение
о готовой публичной странице истории выплат.

Существующие программы без нового schedulePolicy сохраняют прежние строгие окна.
Не было миграции IGW/QIANQI или изменения исторических записей. Проверка snapshot
по-прежнему требует соответствия балансов на одном finalized-блоке. Технический
freshness/RPC-бюджет для production задаётся отдельно; тестовые 600 секунд не
переносятся автоматически на реальную сеть с большей задержкой finality.

## Проверки и границы

- `npm run test:pw-launch`: fork настоящего Pons, полный граф, восстановление
  каждого шага, неизвестный результат, неверные запросы/роли/код, 40-дневный разрыв.
  Fork читает существующий Alchemy через шлюз с лимитом 300 запросов и запретом
  публичных отправок. Все подписанные транзакции исполняются только в Hardhat.
- `node tests/holders/execution.mjs --pw`: два начисления с пропущенным календарным
  периодом, сохранённые долги, распределение перенесённых средств и сверка.
- `node tests/holders/admission.mjs`: прежние правила admission, RLS, reorg и
  неизменяемость первого принятого candidate.
- `node --test tests/unit/holder-schedule.test.mjs`: окна и позднее завершение
  первого принятого снимка, совместимость старой политики.

Coordinator пока допускает только `pw-fork-rehearsal` с конкретным Hardhat
instanceId. Публичного переключателя подписания и HTTP-маршрута нет. Для реального
запуска нужны выбранные адреса, gas-бюджет, публичный admission, подключение owner UI
и создание рабочих политик/служб. Локальный fork не доказывает стоимость исполнения
на Orbit, доступность RPC в будущем или разрешение реального кошелька владельца.

Следующий пакет: газ больших holder-списков и ограниченные production-политики,
затем owner UI и handoff в workers с предварительным просмотром перед активацией.
