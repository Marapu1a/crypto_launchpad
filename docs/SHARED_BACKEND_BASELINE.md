# Общий бэк: первый этап изоляции — 09.10.2026

Владелец согласовал минимальный общий бэк для двух тестовых проектов, без денежных
операций. Архитектурный ориентир из [GPT_REVIEW_RESPONSE](GPT_REVIEW_RESPONSE.md):
общие API/хранение/чтение сети, отдельные финансовые исполнители и права проектов.
Этот пакет реализует только хранение, публичное чтение и границы тестовых заданий.
QIANQI пока не подключён и не переключён; существующий local worker не переписан.

## Принятые границы первого этапа

- Одна PostgreSQL, общий код API, явный UUID проекта во всех проектных связях.
- Отдельный идентификатор экземпляра модуля, версия adapter и config hash.
  Позиция обработки относится к модулю проекта, а не всему серверу.
- Домен выбирает публичный проект по серверной allowlist. Он не является
  авторизацией владельца. Административных и финансовых HTTP-операций здесь нет.
- API не читает ключи, не создаёт транзакции и не импортирует финансовый worker.
- Политики RLS и составные FK дополняют фильтры project_id в коде. Общая роль API
  технически может установить другой контекст через SQL: защита от компрометации
  всего процесса/DB-admin этим не обеспечивается. Граница HTTP не даёт такой SQL.
- Кэш ответов пока не вводится: `Cache-Control: no-store`. Проектный кэш с версиями
  и blockHash будет отдельной частью pipeline; смешивать ответы сейчас нечему.
- Jobs — только `refresh-view`, не команды перевода средств. Лизинг финансового
  signer, fencing и восстановление его журнала остаются будущим пакетом.

## Реализация

Миграция `db/migrations/001_projects.sql` создаёт schema `launchpad`:

| Таблица | Назначение |
|---|---|
| projects | UUID, slug, сеть, адрес токена, публичное имя, test/shadow/paused |
| project_domains | Однозначная привязка hostname к проекту |
| module_instances | (project_id, id), kind, adapter_version, program_address, config_hash |
| project_cursors | (project_id, module_id), целый номер блока и blockHash |
| jobs | (project_id, id), module_id, dedupe_key, состояние refresh-view |
| schema_migrations | Версия и checksum миграции |

Составные foreign keys запрещают приписать курсор/задание одному проекту,
сославшись на модуль другого. Dedupe key и job ID могут совпадать у разных проектов.
Сеть+токен уникальны. Block number хранится в NUMERIC и отдаётся строкой, без
преобразования в JS float. Таблиц денег, билетов или signer intents пока нет.

Роли разделены:

- `lp_owner`: NOLOGIN, владелец схемы; миграции запускаются доверенным администратором.
- `lp_api`: SELECT на projects/modules/cursors и ограниченный resolver домена.
  Нет доступа к таблице jobs и полного SELECT на таблицу доменов, нет прав записи.
- `lp_jobs`: чтение проектных таблиц, INSERT/UPDATE jobs/cursors; нет изменения
  projects, domains, версий и конфигураций модулей.

Для проектных таблиц включены ENABLE и FORCE ROW LEVEL SECURITY. Без контекста
проекта чтение пустое. Контекст ставится через `set_config(..., true)` внутри
транзакции на одном выделенном соединении, очищается на COMMIT/ROLLBACK.
API использует read-only транзакции; фильтры project_id сохранены и в запросах.
Resolver домена — ограниченная SECURITY DEFINER функция с фиксированным search_path;
она читает только таблицу публичной маршрутизации, без динамического SQL.

Мигратор сериализуется advisory lock, применяет изменения и запись checksum
атомарно. Повтор той же версии допустим, несовпадающая версия/checksum — ошибка.
API-процесс не выполняет миграции. `claimViewJob` использует транзакцию и
FOR UPDATE SKIP LOCKED, не выдавая одну queued-задачу двум параллельным вызовам.
Возврат зависшей running-задачи и реальное исполнение заданий ещё не реализованы.

## API и запуск

`npm run start:shared` запускает отдельный read-only API на loopback:4180
(`SHARED_PORT` меняет порт). Нужна `SHARED_DATABASE_URL` с ролью lp_api;
неверная роль/superuser/BYPASSRLS при старте отклоняются. Секретные URL не логируются.
Существующие UI и `/api` запуска Pons работают отдельно и не изменены.

Единственный маршрут: `GET /api/project`. Host `alpha.localhost` и `beta.localhost`
в тестовой базе возвращают разные проект/модули/cursors. Например:

```
curl -H "Host: alpha.localhost" http://127.0.0.1:4180/api/project
```

Неизвестный Host получает 421, некорректный — 400, неподдержанный путь/query — 404,
методы записи — 405. `X-Forwarded-Host`, `X-Project-Id`, query/body не выбирают проект.
Перед публичным использованием прокси обязан контролировать Host; CORS/Origin
не используются как права доступа. Это публичные данные токена, не приватный кабинет.

Для отдельной пустой локальной БД администратор предварительно создаёт роли
lp_owner (NOLOGIN), lp_api/lp_jobs (LOGIN, NOSUPERUSER, NOBYPASSRLS), назначает
lp_owner владельцем выделенной БД и задаёт секреты runtime-ролей. Затем:

```
npm run migrate:shared
```

Команда требует `SHARED_MIGRATION_URL` с правом SET ROLE lp_owner. Пароли, режим
аутентификации и права подключений рабочей БД не выводятся из тестового конфига.

## Проверка на реальном PostgreSQL

`npm run test:shared` использует установленный PostgreSQL (`PG_BIN` — каталог
бинарников, по умолчанию Windows PostgreSQL17). Создаёт **новый** кластер в
`.local/test-results/shared-<timestamp>/pgdata` на свободном loopback-порту.
Режим trust используется только для этого изолированного синтетического теста,
не предлагается для рабочей БД. Остальные локальные PostgreSQL-службы не меняются.
После проверки кластер останавливается; данные, dump и отчёт остаются локально.

Проверено на PostgreSQL 17.2, 5 интеграционных сценариев PASS:

1. Host routing, запрет подмены через query/proxy headers, read-only HTTP, no-store.
2. RLS без scope и с чужим scope, запрет записи API и чтения jobs/domains,
   невозможность принять роль владельца.
3. Составные FK и RLS при записи, одинаковые job ID/dedupe key у двух проектов,
   конкурентный claim и невозможность изменить чужое задание.
4. 24 перемежающихся параллельных HTTP-запроса через пул и rollback без утечки
   контекста проекта в повторно используемое соединение.
5. pg_dump/pg_restore в другую БД: совпадение обоих проектов, сохранение RLS/ACL.

У проектов разные токены и программы; одинаковый синтетический wallet address
использован как dedupe key задания. Это проверка изоляции хранения/jobs, не билетов
или финансовой логики, которых в этом пакете нет.

Отчёт: `.local/test-results/shared-2026-10-09T09-32-38-838Z/report.json`, рядом dump.
Первый запуск выявил наследование pipe handles PostgreSQL-процессом на Windows;
launcher исправлен на spawn с закрытыми потоками и ожиданием exit самого pg_ctl.
