# Вотчер: карточка кошелька и уведомления

20.10.2026, локальный пакет поверх незакоммиченной работы монитора и billing.
Владелец согласовал Web Push и существующий Telegram-бот @qianqi_hub_bot.
Подписка отложена; отдельные доработки Apple не входят в пакет.

## Что реализовано

- Карточка открывается в `dialog`: закрытие кнопкой, Escape и по фону, возврат
  фокуса к списку. Старые счётчики недоступной истории удалены.
- Выбор 5/30/60 минут над списком действует и в разбивке по токенам.
- Общая стоимость доступных позиций Pons. Неизвестные/ненадёжные оценки не
  превращаются в ноль; частичная сумма помечается. Это не весь баланс и не ETH.
- Отдельный SQLite-архив `trades.sqlite3`: сделки сохраняются до фильтра buy/curve,
  ключ token/event-id, монотонный курсор, 28 дней хранения. Данные берутся из уже
  запрошенных страниц; архив не добавляет Pons/RPC-запросов. Первое сохранённое
  значение quoteUsd — оценка курса при наблюдении, не исторический курс сделки.
- Топы 5/30/60 рассчитываются из архива, а не суммированием обрезанных топов.
  Пропущенные/неполные пятиминутки явно дают неполное покрытие.
- Правила подписаны сессией владельца: отслеживаемый адрес, порог отдельной
  покупки в USD, опционально первый замеченный новый токен, Push/Telegram/оба.
  Условия объединяются через ИЛИ; нулевой порог означает любую оценённую покупку.
- Не более одного сигнала на наблюдаемый адрес для пользователя за минуту.
  Это ограничение частоты, не сводка: подавленные события не пересылаются позднее.
- PostgreSQL хранит правила, устройства, привязки, наблюдавшиеся токены,
  курсор и очередь доставки. До 50 правил и 5 устройств на пользователя.
- Первый запуск ставит курсор на конец архива. Сделки до включения правила и
  старше 15 минут не уведомляются; неизвестный USD не проходит денежный порог.
- Очередь: повторная обработка не создаёт дубликаты; ограниченные повторы,
  учёт Telegram 429, удаление истёкших Push-подписок. При отключении канала,
  удалении правила или окончании доступа отложенная доставка отменяется.
  Сбой после внешней отправки и до commit может дать повтор: exactly-once
  Telegram не обещается. Web Push использует tag события.
- Service Worker только для уведомлений; приватные ответы не кеширует.
  Клик открывает карточку, адрес перехода ограничен нашим origin и `/wallets`.

Сфера наблюдения не стала всем Pons: collector по-прежнему получает выбранные
недавние запуски. Таблица сохраняет прежний фильтр первого часа на curve без
создателя; уведомления используют все замеченные покупки этих токенов, включая
pool. «Новый токен» значит впервые замеченный после включения слежения, а не
первую покупку за всю жизнь кошелька. Период сбора — 5 минут плюс отставание
индексации; этот пакет не обещает мгновенное обнаружение.

## Telegram без второго poller

Токен владельца найден по инструкции `PROJECT_BOT.md` в `apps/hub/hub_key.txt`.
Он не копировался. `telegramTokenFile` ссылается на существующий приватный файл.

В existing `server/project-bot/` добавлен необязательный bridge. Команды каталога
работают как раньше; только личные `/start pw_<одноразовый код>` и `/stop`
передаются в API вотчера. Ссылка действует 10 минут. Секретный ingress принимает
только ограниченные JSON-запросы с `X-Telegram-Bot-Api-Secret-Token`.
Webhook Telegram не переключается и `getUpdates` второй раз не запускается.
Если API вотчера недоступен, бот предлагает повторить действие; каталог остаётся
доступен. Пользователь подтверждает связь кнопкой «Проверить подключение».

## Подготовка включения

Локальные приватные конфиги уже созданы в `.local/monitor-alerts/`:
`config.json` и `bridge.json`. Сгенерированы отдельные VAPID-ключи и bridge-secret;
реальная доставка выключена (`enabled:false`). Эти файлы не включать в Git,
логи или общедоступные release archives. Примеры без секретов — в
`ops/market-monitor/alerts*.example.json`.

1. Подготовить приватный конфиг на целевой машине: собственные VAPID-ключи,
   `subject`, путь существующего bot-token, общий bridge-secret. На Linux — 600.
   В конфиг billing добавить `alertsFile`; активный процесс уведомлений использует
   его пул БД и аутентификацию, но не вызывает RPC. Платежи включать не требуется.
2. Применить `node scripts/migrate-monitor-alerts.mjs <billing-config>` через
   роль с правом создать схему. Выдать рабочей роли необходимые права на схему,
   таблицы и sequence. Финансовые таблицы миграция не меняет.
3. Обновить collector, API и статические файлы включая `/alerts.js`, `/sw.js`.
   Проверить nginx: `/api/` идёт в authenticated API :4198; внутренний
   `/api/observed-trades` и `/api/refresh` снаружи закрыты. Пример nginx обновлён;
   его синтаксис надо проверить `nginx -t` на целевой машине до reload.
4. Передать существующему боту `PW_ALERTS_BRIDGE_FILE=<private bridge config>`
   при штатном перезапуске его единственного процесса. Сохранить offset/lock.
5. Включить `enabled:true`, перезапустить API; зайти владельцем, подключить
   браузер и Telegram, явно нажать тест каждого канала. Проверить возврат в
   карточку, отключение и `/stop`. Не подключать рассылку другим пользователям
   до этой проверки. Оплата остаётся выключенной.

Текущий локальный макет: http://127.0.0.1:4221/wallets — демонстрационные данные,
без настоящей отправки. Реальный бот не перезапускался, сервер этим пакетом
не обновлялся. Сквозная доставка в живые Telegram и браузер ещё не проверена.
