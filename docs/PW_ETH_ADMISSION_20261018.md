## Локальная репетиция сумм — PASS

`npm run test:pw-eth-amounts` читает параметры из
[профиля PW](../tokens/PatternWatcher/preparation.json), а не подставляет маленькие
тестовые пороги. Проверено:

- Билет 0,001 ETH: за один wei до порога билета нет; следующая покупка на один wei
  завершает накопление. Миллион билетов не ограничивается продуктовым потолком.
- Фонд и минимальная единица приза 0,005 ETH: через 30 дней фонд на один wei меньше
  отклоняется, ровно порог принимается.
- Выплата холдеру 0,0005 ETH: долг на один wei меньше сохраняется; добавление одного
  wei следующим периодом позволяет выплатить ровно порог. Повторная выплата
  отклоняется. Пауза публикаций не мешает рассчитаться по завершённым периодам.
- Две модельные покупки по 0,5 ETH дают по 500 билетов. Модель creator tax 3%
  направляет 0,018 ETH холдерам, 0,006 draw и 0,006 проекту. Draw проходит настоящую
  проверку сохранённого BLS beacon; сумма приза и переноса равна фонду.

Это проверка арифметики наших контрактов, а не модель цены реальной кривой:
fixture не включает долю creator от базовой комиссии Pons, снайперский сбор,
проскальзывание и graduation. Split применяется к фактически полученным комиссиям.

Отчёт: `.local/test-results/pw-eth-amounts-2026-10-18T20-04-00-105Z/report.json`.
После двух holder-периодов: получено 0,018 ETH, начислено/выплачено 0,001 ETH,
свободно 0,017 ETH. Измеренные локальные gas units сохранены в отчёте; это не цена
production-транзакций и не утверждённый газовый бюджет.

Соседний полный EVM/PostgreSQL сценарий, включая смену publisher и перезапуск:

## Реальные контракты — чтение

На публичном RPC Robinhood, числовой блок **92039157**:

- Factory/router/escrow/hook совпали с `config/pons-production-pins.json`.
- `launchEnabled=true`; config 0 включён; native pair — zero address.
- Launch fee 0,0005 ETH, cap creator tax 10%, базовая curve fee 1%.
- Текущий launch helper `0x3711ceA4feaDE896C913C68F01Eda97Cb06D1A42`, runtime hash
  `0xeade22566c766377f6adfb99534f2772251efad9568642c0704a7051418e624c`.
  Sourcify exact match подтверждён. Factory имеет `setLaunchDeployer`: совпадение
  кода factory само по себе не фиксирует её helper, его нужно проверять отдельно.

Источники: [официальные Pons v2 docs](https://docs.ponsfamily.com/v2),
[исходник factory](https://sourcify.dev/server/v2/contract/4663/0x7eD598BcEf8bd9Edd8C97A195C6d13f40801EC7e?fields=all),
[исходник helper](https://sourcify.dev/server/v2/contract/4663/0x3711ceA4feaDE896C913C68F01Eda97Cb06D1A42?fields=all).
Численные настройки — результат прямого RPC-чтения на указанном блоке, не вечные
константы. Перед реальным запуском их следует перечитать.

Образец token `0x597113bd319eb670e7cb662ad8149f68fa237e88` пересобран из исходников
`stdJsonInput` проверенной factory компилятором Solidity 0.8.35. После подстановки
его immutable deployer/curve/factory runtime совпал целиком:
`0xb2b353462b13721e9499f6d58b9e8942885596dee25c3e1f998192d0b59668c4`.
Это обычный ERC20 с ERC20Burnable, без proxy/rebase и доступного внешнего mint;
эмиссия создаётся конструктором на curve. Добровольный burn уменьшает и баланс,
и totalSupply: проверка суммы балансов остаётся применимой.

Hash образца нельзя назначать будущему PW: immutable-адреса будут другими.
При admission PW потребуется сопоставить его runtime с тем же проверенным
шаблоном и конкретными адресами запуска. Полный список держателей образца не
собирался; production holder admission этим исследованием не выдаётся.

## Симуляция запуска — CALL_ACCEPTED

На блоке **92041199** реальная factory приняла `eth_call` запуска с native pair,
creator tax 300 bps, отключённым buyback и существующим контрактом в качестве
получателя комиссий. Вернулись рассчитанные token/curve адреса, но ничего не
создавалось. В симуляции использовались исторический launcher и временный
`balance` override; счёт не пополнялся. Без override образец имел нулевой ETH
баланс и симуляция отказала — этот неуспешный результат сохранён отдельно.

Это проверка интерфейса реальной factory, а не полного запуска PW. Stand-in
получатель — не наш ещё не развёрнутый collector; реальные права/баланс будущего
owner, collector bind, весь набор deployment-транзакций и их восстановление
после сбоя предстоит проверить вместе.

## Бесплатное чтение и границы

Публичный RPC вернул finalized block **92028423**, но уже не имел его состояния
для `eth_getCode`. Чтение на свежем числовом latest-блоке прошло; оно не подменяет
finalized-проверку в денежном журнале.

Существующий endpoint Alchemy прошёл отдельную проверку за **7 RPC-запросов**:
chainId, finalized block **92032327**, код token, totalSupply, balanceOf(curve),
повторный hash блока и проверка нерегрессирующей finality. Ключ не публикуется.
Тариф аккаунта не проверялся. Это доказательство доступности выбранного состояния
в момент проверки, не гарантия хранения любой истории или будущих лимитов.

При проверке finalized отставал примерно на 879 секунд. Тестовый freshness=600
секунд нельзя автоматически переносить в production. Нужно согласовать cutoff,
получение списка Pons и допустимое окно проверки; расхождение балансов должно
останавливать admission, а не незаметно менять дату снимка.

План нагрузки сохраняется: Pons — источник торговой активности; RPC — ограниченные
проверки при запуске, принятии месячного снимка и исполнении. Частого фонового
опроса этот пакет не добавляет. Общая проверка журнала также требует доступности
исторических receipts/state; готовность всего архива данным тестом не доказана.
