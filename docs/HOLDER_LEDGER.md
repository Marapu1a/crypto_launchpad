## Что делает пакет

1. Собирает страницы через переданную функцию `fetchPage(cursor)` с явными лимитами.
2. Проверяет цепочку курсоров, токен, метаданные, уникальность адресов, число
   держателей и сумму целочисленных балансов против supply. Неполная выгрузка,
   повтор курсора, смена метаданных и ошибка источника останавливают сбор.
3. Сохраняет исходные страницы и время наблюдения в candidate, вычисляет его hash.
   `share` и labels не определяют суммы или допуск. Согласованность страниц
   не означает атомарность; `atomicity` остаётся `unverified`.
4. Рассчитывает раунд только после явного `acceptFixtureSnapshot` с причиной.
   Поддержана только отметка `fixture-only`; production acceptance отсутствует.
5. Ведёт изолированные средства, начисления, резервы отправок и результаты
   в воспроизводимом JSON-журнале событий.

`chainId` источника задаёт вызывающий код: текущий ответ Pons сам его не доказывает.
При ошибке коллектора пригодный к расчёту частичный снимок не возвращается;
архивирование ответов до завершения сбора — обязанность транспортного адаптера.

## Расчёт и перенос

Экземпляр изолирован по `projectId + chainId + token + asset`; события содержат
hash этого контекста. В фонд заносятся только явно переданные поступления,
предназначенные держателям. Комиссии розыгрышей и газ сюда не относятся.
Реальное поступление должен подтвердить будущий адаптер: событие `credit`
само по себе не доказывает получение денег. Его receiptId должен быть стабильной
идентичностью поступления, а не случайным ID попытки обработки.

Поддержанный вариант расчёта; утверждённые параметры PW указаны в [правилах](PATTERN_WATCHER_RULES.md):

- `weight: snapshot-balance`, веса пропорциональны балансу в принятом снимке;
- явные `exclusions`, `minimumHolding` и `minimumPayment`, без defaults;
- доля кошелька = floor(budget × balance / eligibleBalanceSum), bigint;
- остаток целочисленного деления остаётся свободным фондом для следующего раунда;
- начисление ниже порога выплаты остаётся долгом конкретному кошельку и складывается
  с будущими начислениями. Оно не возвращается в свободный фонд;
- продажа токенов или исключение адреса в следующем раунде не стирают прежний долг.

Равенство проверяется при каждом воспроизведении:
`получено = свободно + начислено, но не выплачено + выплачено`.
Резерв отправок — часть невыплаченного, а не дополнительная сумма.
Раунды с повторным roundId или periodId отклоняются; расписание раз в месяц
здесь не исполняется, periodId задаёт будущий планировщик.
Нет допускаемых держателей — нет раунда и списания средств.

## Журнал выплат

| Состояние | Учёт и следующий шаг |
|---|---|
| prepared | Сумма зарезервирована из долга; можно отменить до отправки |
| submitted | Зафиксирован txHash; средства остаются зарезервированы |
| unknown | Ответ потерян; сначала сверка того же txHash, резерв сохраняется |
| confirmed | Долг и резерв уменьшены, сумма учтена как выплаченная |
| failed | Только после подтверждённого неуспеха; резерв освобождён, долг сохранён |
| cancelled | Подготовка отменена до отправки, долг сохранён |

Повтор точно того же события не меняет результат. Тот же ID с другим содержимым
отклоняется. Повторная отправка зарезервированного долга и повторное использование
txHash запрещены. Подготовка берёт порог из последнего принятого раунда;
старой политикой нельзя обойти новый минимум. Уже подготовленная сумма фиксирована.
Тестовое подтверждение связывает txHash, сеть, актив, адрес и сумму и требует
`finalized: true`. **Это модель доказательства**, не проверка реального receipt.

## Границы реализации

- Нет финансового исполнения, автоматических HTTP-запросов, fee split контракта,
  API владельца или подключения к работающим токенам.
- Нет проверки production finality, канонического transfer receipt, сохранения
  подписанных транзакций, nonce/replacement или сверки фактического баланса фонда.
- Журнал полностью воспроизводится при операции. Это опорная модель для небольших
  репетиций; для длительной эксплуатации нужны транзакционная БД/CAS, блокировка
  экземпляра, доверенные источники событий и проверяемые контрольные состояния.
- Файловое сохранение есть только в тестовом сценарии с одним писателем. Оно
  не объявлено готовым конкурентным хранилищем.

Следующий интеграционный пакет: реализация утверждённой политики PW и допуска снимка,
подключение изолированного фонда к общей платформе, durable storage и read-only
preview. Реальные отправки — отдельный этап после проверки этих границ.
