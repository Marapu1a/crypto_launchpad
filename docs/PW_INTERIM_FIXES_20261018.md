# Исправления после промежуточного ревью PW

18.10.2026. База — `2b5d3d1`, ответ GPT сохранён без изменений в
[исходном ревью](GPT_INTERIM_REVIEW_20261018.md). Все изменения локальные;
сборки и deployed экземпляры IGW/QIANQI не менялись.

## F1: источник финансовых событий

В профиле с fundingPolicy общий `appendHolderPreparation` запрещает
fee.received/holder.deposited, даже если передан правильно оформленный receipt.
Запись доступна только через неэкспортируемую функцию, вызванную importer.
После захвата строки FOR UPDATE повторно проверяются finalized height и
канонический blockHash. Все ABI/getter/RPC проверки повторно не выполняются:
их первая проверка привязана к тому же неизменному блоку.

Fixture-начисление запрещено для observed-funding профиля и в API, и при replay.
Прежние fixture-only профили сохраняют тестовый путь; они не переименованы в live.
`lp_jobs`/администратор БД по-прежнему доверенные субъекты: прямой SQL или
компрометация процесса не устраняются приватной JS-функцией. Checksum не подпись.

## F2: политика запуска

Добавлен `feePolicyKind`:
- `draw-prizes-team-operations-v1` — существующий generic draw graph;
- `pw-holders-draw-project-v1` — PW, запуск запрещён до готовности выплат.

Gate применяется при проверке входа, production profile, создании coordinator,
при повторном использовании сохранённого input и worker policy admission.
Он действует по политике, не по названию токена. PW preparation помечен явно.
Для production ETH оператор обязан закрепить generic feePolicyKind в profile;
поля клиентского запроса недостаточно. Legacy USDG inputs не перезаписываются.
Существующие generic rehearsal ETH продолжают работать.

Имя токена само по себе не резервируется: намеренно выбранный оператором generic
профиль остаётся generic, даже если назвать его PW. Автоматического угадывания
продуктовой политики по имени нет. Профиль PW нельзя превратить в generic через UI.

## F3: прямые пополнения

Для будущего PW создан отдельный `contracts/holders/NativeHolderCollector.sol`.
Он учитывает только ETH, полученный receive-callback от закреплённого escrow
внутри collect(). forward() передаёт только forwardableFees, обнуляя их до вызова;
revert восстанавливает состояние транзакции. Прямой и forced ETH остаются в
quarantined() и не создают Revenue. Автоматического возврата/распределения этих
средств нет; не отправлять туда реальные пополнения. Это не готовый production-релиз.

Наблюдатель требует accountingVersion и token нового collector, кроме прежних
runtime pins/bindings. Старые draw collector и native build не изменены.
Старый локальный holder fixture с прежним collector не мигрируется незаметно:
для новой сборки создаётся новая изолированная конфигурация.

Доверяем происхождению зачислений внутри закреплённого Pons escrow. Эта проверка
не доказывает отдельно каждую торговую сделку или запрет посторонних депозитов
в самом escrow. Она устраняет смешение прямого баланса collector с его fee counter.

## F4: сверка после восстановления и перед расчётом

`reconcileHolderPreparation` по явному запросу перепроверяет сохранённые receipts,
runtime pins, canonical/finalized branch, накопительные суммы splitter/vault и
покрытие полученных средств балансом накопительного vault. Пропуск, уменьшение
finality, нехватка баланса или смена блока завершают сверку ошибкой. Журнал не
откатывается автоматически и недостающие суммы не выдумываются.

Есть предел числа проверяемых событий: по умолчанию 1000, максимум 10000;
превышение — отказ, не частичный успех. Это не фоновый scanner: полный проход
вызывается явно при восстановлении/подготовке раунда. Большие истории потребуют
checkpoint/reconciliation оптимизации перед эксплуатацией, не платного polling.

Сверка идёт без долгой блокировки БД; после RPC сравниваются revision и hash.
`readReconciledHolderPreparation` дополнительно связывает preview с той же
ревизией. Обычный preview показывает `funding-reconciliation-required`.
Успешная сверка не принимает снимок и не разрешает выплаты: executionEnabled=false.
Будущий seal обязан использовать этот путь и сохранить границу ревизии/проверки.
Production scheduler/seal пока отсутствуют — автоматического включения не было.

Баланс vault проверяется по текущей модели без вывода средств. После реализации
выплат формулу нужно дополнить paid/liabilities; нельзя молча оставить старое условие.
Финальность RPC остаётся доверенной предпосылкой; атомарной транзакции между
блокчейном и COMMIT PostgreSQL не существует.
