# Билеты поверх общей истории: локальное shadow-сравнение

09.10.2026. Пакет поверх `eb2c174`. Реализация:
`server/shared/ticket-shadow.mjs`, миграция `003_ticket_shadow.sql`.

Общий reader хранит полные блоки/receipts; новый потребитель рассчитывает билеты
каждого модуля в своей PostgreSQL-записи. Прежний файловый индексатор продолжает
работать отдельно и служит базой сравнения. Финансовый worker не переключён.

## Привязки и хранение

`registerTicketShadow` принимает профиль, полученный через существующий
`createProfile`. Проверяет project/token/chain, module/program, версию адаптера
`local-ticket-shadow-v1`, Pons factory/router/USDG, anchor общей истории,
код и getters контрактов, экземпляр локального fork. Разрешён только профиль
`launchpad-local-ticket-profile-v1`, localhost chain31337 с fork4663.
Повторная регистрация той же пары project/module не заменяет профиль.

`ticket_shadows` отделён от raw cursors и token-only inbox. Ключ составной:
project/module, FORCE RLS. `lp_jobs` может читать и создавать записи, обновлять
только состояние/его checksum/курсор. Profile/source bindings неизменяемы этой
ролью. Публичный API и ingest-роль доступа к таблице не получили.

**Профиль и состояние хранятся как точный JSON-текст**, а не jsonb. Существующий
digest чувствителен к порядку ключей; jsonb меняет его. Это важно для домена
подтверждений и bundle hash. Проверенные bundles сохраняются внутри состояния
с первоначальным порядком ключей и доступны после удаления внешних файлов.
Raw blocks остаются jsonb: они не используются как исходный байтовый bundle.

Регистрация — внутренний вызов для доверенной конфигурации, не административный
HTTP endpoint. Как и в базе, RLS не защищает от скомпрометированного runtime,
который сам выбирает другой project scope; публичного доступа к нему нет.

## Обработка

`applyTicketShadow` читает **полную** общую историю, а не `project_evidence`:
отдельный PurchasesRecognized может вообще не содержать transfer токена.
Используются прежние `recognize`, `deferDecision`, `creditedEvents`,
`replayTickets`. Проверяется непрерывность, принадлежность receipts ветке,
целостность профиля/состояния. За пакет можно обработать до 500 блоков.

Сохраняются прежние правила:

- opening buy и прямые покупки считаются по net debit; порог и остаток отдельные;
- неподдержанные маршруты не становятся подтверждёнными от наличия файла;
- поздняя покупка входит в cutoff по `creditedAt`, исходное событие не меняется;
- bundle проверяется по hash, profile domain, authority, runtime и исходной покупке;
- повторная доставка покупки новым commitment сохраняет первое начисление;
- отсутствующий/неверный bundle откатывает весь пакет и не двигает курсор;
- состояние и курсор записываются одной транзакцией, параллельные применения
  одного модуля сериализованы. Ошибка A не блокирует обработку B.

Полные блоки и receipts повторно из RPC не читаются. Проверки runtime/getters,
fork instance и canonical hashes пока выполняются через RPC для каждого профиля.
Следовательно, **это не полностью без-RPC обработка** и прежнее измерение 21/42
относится только к транспортной фикстуре, не ко всему ticket pipeline.
Чтения проверки выполняются внутри проектной транзакции; это допустимо для
локального shadow, но требует отдельной оптимизации/таймаутов перед эксплуатацией.

Общий source-lock удерживает ветку БД во время применения. При source halt,
изменении runtime/instance или несоответствии ветки новые расчёты запрещены.
Автоматического reorg replay нет. Диагностический `readTicketShadow` по-прежнему
позволяет прочитать сохранённое состояние, в том числе остановленное.

## Снимки

`freezeShadowSnapshot` создаёт **снимок для сравнения**, не запрос розыгрыша.
Он использует прежний `snapshotTickets`, сохраняет cutoff и нормализованные
consumed ranges как неизменяемый вход. Тот же label с другим входом отклоняется.
Старый cutoff после позднего начисления даёт прежних участников.

Consumed ranges здесь передаёт тест/внутренний caller. Нет чтения текущего
on-chain cycle, резервирования билетов, финансового исполнения или подписи.
Нельзя передавать shadow snapshot финансовому worker как готовую авторизацию.

## Проверки

Команда: `npm run test:shared:tickets`. Требуется уже запущенный локальный Pons
fork на 127.0.0.1:8545. Тест не сбрасывает fork, создаёт собственные два токена,
программы и recognition source. Тестовые покупки идут только в localhost31337.
PostgreSQL поднимается в новом отдельном каталоге и останавливается после теста.

Сравнение выполняется с **неизменённым алгоритмом `scanTickets`** на тех же
реальных receipts локального fork. В старом модуле лишь экспортирована функция
`verifyProfile`, чтобы не ослаблять защитные проверки нового пути.

Проверяются события, evidence, wallets, carry, head/profile, участники и hashes
снимков. Первый токен: opening6 + deferred4 USDG, порог10; второй: opening1,
порог1. Позднее подтверждение переводит первый с остатка6 к одному билету,
старый cutoff остаётся пустым. Покупка другого кошелька остаётся ожидающей.
Отдельно проверены отсутствующий/повреждённый bundle, независимый прогресс B,
параллельные повторы, restart без старого bundle, повторная доставка, запрет
смены замороженного входа, RLS, immutable profile, runtime/instance drift,
повреждённое состояние, reorg halt и backup/restore точного ticket state.

## Что остаётся

Это ограниченный shadow-адаптер: состояние хранится одним JSON-текстом и ledger
пересчитывается по накопленной истории. Это удобно для точного сравнения, но не
готовое масштабируемое хранение длительной истории: нормализованные события,
начисления, snapshots и инкрементальная обработка — отдельный следующий этап.

QIANQI production не подключён и не изменён. Не перенесены неизвестные маршруты/
traces, pool/native, production finality и clock. Финансовый журнал/исполнитель,
ключи, эксплуатационный scheduler и cutover остаются отдельными пакетами.
