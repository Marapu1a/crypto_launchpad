## Матрица конструктора

| Возможность | Что позволяет найденная реализация | Решение для нашего UI |
|---|---|---|
| Имя, тикер, logo, описание, соцсети | Передаются в TokenParams | Своя форма и публикация metadata; проверка форматов |
| ETH / ERC-20 pair | Native либо разрешённый Pons актив | Только реально доступные пары; MVP USDG |
| Supply, кривая, graduation, параметры pool | Выбор протокольного launchConfig; для ERC-20 отдельная pairTokenEconomics | Показывать условия выбранной конфигурации; не обещать произвольные поля |
| Creator tax | Пользователь задаёт bps в пределах cap и общего fee limit | Процент отдельно от base fee; до подписи показать полную стоимость торговли |
| Получатель creator fees | Явный адрес, включая наш collector | Для модуля программа назначает свой отдельный collector |
| Buyback & vest | Есть отдельный флаг и механика | Совместимость и учёт заблокированных токенов проверять; для первого шаблона предложить off, ещё не решение |
| Opening buy | Отдельный launch-and-buy путь | Отдельная интеграционная проверка; не добавлять обычную покупку как якобы атомарную |
| Дополнительные snipe exemptions | Перегрузка launchToken с адресами, предел в исходнике 32 | Не включать без продуктовой необходимости; влияние на ранние покупки раскрывать |
| Предсказание адреса | Salt и CREATE2 | Сохранить salt и рассчитанные адреса в deployment plan |

## Существенные выводы для архитектуры

1. **Получатель комиссий — роль, а не только адрес выплаты.** В исходнике
   `transferCreatorFeeRecipient` разрешён текущему recipient. Включение buyback
   также доступно recipient; protocol owner может его выключить. Если recipient —
   наш контракт, нужные методы управления надо проектировать явно. Свободный вывод
   будущего дохода из программы нельзя незаметно добавлять как техническую функцию.
2. **Один collector на экземпляр.** Escrow interface хранит баланс recipient/asset,
   а не отдельный баланс каждого нашего проекта. Общий recipient усложнит доказуемое
   разделение средств; предлагаем отдельный адрес на токен.
3. **Фонд — только полученные средства.** Начисления curve, escrow balance,
   ожидаемая конвертация после graduation и деньги в нашем контракте — разные стадии.
   В порог цикла не включать ещё не полученные деньги.
4. **Свой UI не требует собственного launch forwarder.** Прямой вызов фабрики
   кошельком возможен. `launchTokenFor` в исходнике доступен только доверенному
   forwarder Pons: нельзя предположить, что любой наш factory вызовет его от имени
   пользователя. Предпочтительный первый путь — очередь прямых подписей кошелька.
5. **Модули создаются с учётом раннего BUY.** Открытие торговли следует за launch
   сразу; история должна учитывать launch block. Нельзя начать учёт после завершения
   последнего шага настройки и потерять первые покупки.
