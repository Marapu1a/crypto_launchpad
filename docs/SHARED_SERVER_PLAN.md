## Схема размещения

Один экземпляр PostgreSQL и общий код платформы; отдельные project/module state,
история и журналы. Сначала только приватный read-only shadow QIANQI без signer.
Публичный домен ему не нужен. API платформы при необходимости — `127.0.0.1:4180`.

Новые каталоги отсутствуют на сервере и зарезервированы только предложением:

| Каталог | Назначение |
| --- | --- |
| `/opt/crypto-launchpad/releases/<commit>` | Неизменяемый код, отдельный current symlink |
| `/etc/crypto-launchpad` | Собственная конфигурация с ограниченными правами |
| `/var/lib/crypto-launchpad` | Writable state, bootstrap evidence и bounded captures |
| `/var/backups/crypto-launchpad` | Отдельные backup платформы |

Отдельные OS users для API и shadow, без доступа к приватным данным qianqi.
DB users — по назначениям, migration/admin credentials не выдавать runtime.
Текущие lp_api/lp_jobs поддерживают общий project context: RLS защищает от ошибок
запросов, но не от захвата общей роли. Для финансового multi-project production
нужны роли, привязанные к проекту, отдельные signer domains и проверки отказа
при попытке доступа к соседнему проекту. Текущие роли такой границы не дают.

Для первого shadow предлагается общий лимит новых Node-процессов 1 GiB RAM
и CPUQuota=50% (половина одного ядра), с измерением RSS, задержки и влияния
на QIANQI. Это стартовый профиль для репетиции, не доказанная достаточность.
PostgreSQL имеет отдельный бюджет; его настройки и фактическую память измерить
до длительной работы. Не складывать MemoryMax существующих сервисов как реальное
потребление и не считать весь свободный RAM доступным новому приложению.

## Обязательная подготовка до постоянного процесса

1. Проверить migrations001–008, роли/RLS, import/live cycle, restart и dump/restore
   на PostgreSQL18 в изолированном тестовом окружении. Не устанавливать молча
   серверный default18 по результатам тестов17 и не добавлять репозиторий17 без выбора.
2. Вынести writable paths/bootstrap archive из привязки к cwd и `.local`;
   immutable release должен запускаться с отдельным state root.
3. Ограничить captures и рост PostgreSQL. Сейчас новый head хранит полный payload,
   а live расчёт повторяет историю в памяти. Сначала дедупликация evidence,
   компактные записи head, политика хранения диагностических capture и disk guard.
   Не удалять immutable evidence, необходимое для воспроизведения результата.
4. Подготовить unit/env templates без секретов, проверку конфигурации и остановку
   shadow при нехватке места. Существующие QIANQI units не редактировать.

## Поэтапное включение и критерии

1. **Следующий пакет, локально:** совместимость PostgreSQL18, portable paths,
   ограничение хранения и шаблоны эксплуатации; тест disk guard и restart.
   Это подготовка, не установка на сервер.
2. **Отдельный серверный пакет после согласования:** новые users/directories/DB,
   bootstrap из проверенного публичного evidence и ограниченная репетиция shadow.
   Предварительный срок 24 часа, бюджет новых state/captures 3 GiB; остановка
   нового shadow при превышении бюджета или свободном диске менее 10 GiB.
   Пороги реализовать и проверить до запуска. Проверять рост DB/WAL отдельно.
3. **Критерии репетиции:** прогресс finalized head, повтор без дублей, restart,
   отсутствие расхождений с QIANQI, ограниченный рост данных, отсутствие ухудшения
   доступности/задержек существующего API. Пустой интервал без событий не доказывает
   обработку новых BUY/recognition/draw; если событий нет, этот пункт остаётся открыт.
4. **Backup:** отдельный dump новой БД и необходимого evidence, checksum,
   восстановление в изолированную БД, проверка head/counts/hashes. Код восстановим
   по commit. Новый off-server backup настраивать отдельно; существующий backup
   QIANQI не считается backup новой платформы. Секреты не включать в обычный архив.
5. **Позже:** выбранный владельцем основной домен/поддомены, отдельный nginx vhost
   и TLS, Host allowlist. Текущий общий `/api/project` не заменяет QIANQI `/v1/`.
   Публичное подключение и полноценный контракт API — отдельные задачи.
6. **Перенос финансового QIANQI worker:** только после copied-state rehearsal,
   переноса обязательств/незавершённых RNG/nonce journals и проверки прав.
   Старый worker остановлен до включения нового signer; два исполнителя с одним
   nonce domain запрещены. Этот план не разрешает такое переключение.

Откат серверной репетиции: остановить только новые units, вернуть предыдущий
release платформы при совместимой схеме. При несовместимой миграции — отдельное
восстановление из проверенного pre-migration backup, без потери новых evidence.
Данные сохранить для разбора; QIANQI services/vhost/backup не трогать.
Автоматического purge PostgreSQL или удаления каталогов в откате нет.
