# Общий приём данных цепочки

09.10.2026. Следующий пакет после базы `659cdaf`. Реализация:
`server/shared/chain-read.mjs`, миграция `002_chain_read.sql`.

Один source хранит полные блоки с транзакциями и receipts. Идентичность задана
chain ID, genesis hash и проверяемым anchor. Source UUID отделяет локальные
репетиции; два fork с одинаковым chain ID нельзя автоматически считать одной сетью.
Регистрацию источника и подписок делает доверенный администратор, не публичный API.

`ingestNext(pool, rpc, sourceId, target)` читает максимум один следующий блок.
RPC предоставляет `send(method, params)` (совместимо с ethers provider).
Проверяются сеть, текущий head, parent, принадлежность всех транзакций/receipts/logs
и повторный hash блока после загрузки. Нет receipt — нет продвижения.
Запись блока и head атомарна; конкурентные читатели сериализованы по source.
RPC ограничен 5 секундами на вызов и общим бюджетом чтения 30 секунд;
таймаут освобождает транзакцию, underlying RPC transport должен иметь собственный
таймаут/отмену для очистки сетевого запроса. Ошибку можно повторить.

`applyNext(pool, projectId, moduleId)` независимо продвигает курсор подписки.
Выбирает транзакции с логами адреса токена, сохраняет полные receipts этих
транзакций и курсор одной транзакцией БД. Сохраняются и неизвестные маршруты.
Пустой блок тоже учитывается. Пропуск блока запрещён. Повтор/конкурентный вызов
не создаёт дублей. Ошибка A не мешает B читать уже загруженную историю.

Это **inbox свидетельств**, ещё не начисление билетов. Общие raw blocks содержат
все логи, включая отдельные подтверждения late recognition. Проектный inbox
фильтрует только token address: перед подключением ticket adapter нужно добавить
его registry/program/curve bindings и confirmation bundles. Нельзя использовать
этот inbox как готовый полный источник поздних начислений.
Существующий JSON ticket indexer/worker не переключён: `creditedAt`, frozen cutoff
и финансовые решения продолжают работать прежним путём.

При смене hash сохранённого head source получает durable `halted=true`.
Оба потребителя этого source останавливаются, история не переписывается.
Это общая проблема цепочки, в отличие от ошибки одного проектного потребителя.
Автоматический rollback/replay и снятие halt не реализованы. `target` задаёт границу
чтения, **не доказывает finality**. Production admission/finality остаются открыты.

## БД и доступ

Перед миграцией администратор создаёт дополнительную роль `lp_ingest LOGIN
NOSUPERUSER NOBYPASSRLS` и отдельно назначает безопасную аутентификацию.
Она читает source/blocks, добавляет блоки, обновляет только head/halt;
доступа к проектным данным нет. `lp_jobs` читает raw evidence и имеет RLS-доступ
к подпискам/inbox своего проекта. `lp_api` доступа к raw/inbox не получил.
Подписки создаются отдельно от прежних module cursors: raw application не выдаётся
за прогресс финансового модуля. Мигратор применяет версии последовательно,
проверяет checksum существующих миграций; файл 001 не изменён.

Глобальные raw данные публичны по своей природе, но финансовые данные в них
не добавляются. Runtime не может удалять историю или менять bindings подписок.
Серверный scheduler, CLI запуска постоянного reader и развёртывание пока не входят
в пакет: функции вызываются интеграционным harness на отдельной локальной БД.

## Проверка и границы

`npm run test:shared` — настоящий изолированный PostgreSQL, синтетический RPC:
ошибочная сеть/receipt, gaps, последовательность, retry, два потребителя,
RLS/ACL, reorg halt, backup/restore вместе с предыдущими HTTP-проверками.
Фикстура проверяет транспортную связность, не декодирование реальной покупки.

Измерение вызовов `send`: три блока, две транзакции в каждом, два проекта.
Общий reader: **21 вызов**, два независимых прохода: **42 вызова**.
Проектное применение добавляет **0 RPC-вызовов**. Учитываются chain/genesis/head
guards и повторная проверка блока. Это экономия 50% для этой фикстуры,
не production benchmark и не оценка денежных затрат или диска.

Следующий пакет: проектный ticket adapter поверх shared evidence с проверенными
bindings, late confirmations и отдельным прогрессом интерпретации. Затем shadow
сравнение с прежним индексатором. QIANQI production не менялся.

Итог проверки 09.10.2026: **10/10 DB/HTTP/restore сценариев PASS**, PostgreSQL17.2.
Отчёт: `.local/test-results/shared-2026-10-09T09-48-12-338Z/report.json`.
Backup/restore сверяет также raw blocks, halt, подписки и оба проектных inbox.
Соседний `node --test tests/unit/tickets.test.mjs`: **8/8 PASS**, включая
creditedAt, carry, повторные подтверждения и неизменность старого cutoff.
Это регрессия старого пути, не проверка ещё не подключённого DB ticket adapter.
Первый прогон выявил отсутствие прав для SQL FOR SHARE у read-only роли;
заменено координацией через shared/exclusive advisory locks без выдачи UPDATE.
