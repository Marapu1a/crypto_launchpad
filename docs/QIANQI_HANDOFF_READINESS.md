## Решение владельца

Владелец разрешил перенос QIANQI после проверки готовности кода и дальнейшую
проверку в рабочем режиме. Монета экспериментальная, активность почти нулевая.
Ожидание суток или новой покупки **не является условием переключения**.
Повторное разрешение на сам перенос не требуется.

Это отменяет прежний порядок «сначала суточный shadow, затем следующий пакет».
Сам shadow остаётся вспомогательной проверкой; его прежний deadline и таймеры
этим документом не изменены.

## Результат проверки

**Переключение ещё не готово по коду.** Препятствие — отсутствующий рабочий
адаптер существующего проекта, а не недостаточная продолжительность наблюдения.

| Область | Проверенный код | Что отсутствует |
|---|---|---|
| Исполнитель | `server/shared/postgres-worker.mjs`: `workerFinancialConfig` закрепляет chainId 31337; `registerPostgresWorker` принимает только новый цикл 0 без pending | Подключение существующих RobinhoodShortController, RobinhoodMonthlyController и DualControllerPromoVault в сети 4663 |
| Действующий движок | В rh_project `scripts/pons-automation.cjs` обслуживает оба контроллера, funding, recognition, RNG и выплаты; `scripts/run-pons-public.cjs` загружает зашифрованный keystore и сохраняет operational state | Интеграция этого исполнения с проектным контекстом платформы и сохранением текущего журнала/nonce |
| API сайта | `server/shared/api.mjs` обслуживает только GET `/api/project` | Совместимость с `/v1/` сайта QIANQI; переключение nginx на этот API сейчас даст 404 |
| История и обязательства | Shadow, history, finance и outcome replay сверяют публичную историю | Перенос исполнительного состояния и reconciliation незавершённых отправок, не только публичного ledger |

## Работы непосредственно до переключения

1. Подключить рабочую механику QIANQI как отдельный existing-project adapter:
   оба lane, late recognition/finality, funding, RNG, settlement и claims.
   Не подменять её контрактами нового токена и не отключать проверку chainId.
2. Реализовать совместимый API сайта поверх проектных данных. Простой proxy
   старого API или переименование systemd-службы не считать завершённым переездом.
3. Сохранить текущие durable state/journals и обеспечить восстановление старых
   pending intent с тем же hash/nonce. Проверить это локально, включая Monthly,
   поздние билеты и остановку между broadcast и сохранением результата.
4. Подготовить отдельный production runtime, проектные права и backup/rollback.
   Не использовать ограниченный shadow-service как финансовый исполнитель:
   его deadline и backup могут останавливать процесс.
5. На переключении остановить старого исполнителя, зафиксировать итоговый
   checkpoint и незавершённые операции, затем запустить только одного нового.
   Переключить API после проверки совместимости; проверить первый проход,
   непрерывность состояния и работу сайта. Отсутствие новых покупок не мешает
   принять это переключение, но не доказывает прохождение нового draw.

Следующий пакет — реализация адаптера и совместимого API, затем сам handoff
в пределах уже полученного разрешения. Новое пассивное окно наблюдения не нужно.
