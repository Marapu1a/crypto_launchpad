# Журнал исполнения выплат: локальный пакет

18.10.2026. Основа: [контракт выплат](HOLDER_PAYOUT.md) и
[допуск снимка](HOLDER_SNAPSHOT_ADMISSION.md), Git `2b5d3d1` плюс текущий рабочий пакет.
Реальные ключи, сервер, IGW/QIANQI и публичный запуск не затронуты.

Новый профиль v2 поддерживает [минимальное управление фондом](HOLDER_GOVERNANCE.md);
v1 сохраняет прежнюю привязку publisher.

## Путь данных

1. `registerHolderExecution` связывает локальную политику с сохранённой подготовкой:
   scope, код vault, splitter, publisher и явно выбранный minimumPayment.
   Профили без наблюдаемого funding и trusted admission не подходят.
2. `prepareHolderAllocation` берёт candidate, admission и исключения из PostgreSQL,
   строит план самостоятельно, проверяет поступления и доступный бюджет на
   finalized блоке. Период и план неизменяемы; повтор возвращает тот же план.
3. Внешний локальный тест подписывает точный вызов. `recordHolderTransaction`
   проверяет сеть, адрес, sender, calldata, нулевой value, nonce и лимиты газа,
   симулирует вызов на finalized состоянии и **сначала сохраняет подписанные байты**.
   Модуль не подписывает и не отправляет транзакции.
4. После сохранения вызывающая сторона может отправить именно эти байты.
   До подтверждения журнал хранит `unknown`, даже если отправка не состоялась.
   Отсутствующий или ещё не finalized receipt не снимает блокировку.
5. `resolveHolderTransaction` сам запрашивает receipt, проверяет хеш, сеть,
   runtime/привязки vault и канонический блок. Для выплаты сверяет событие Paid,
   для закрытия начислений — RoundSealed и сумму плана. Прислать готовое
   «успешное подтверждение» вместо проверки через RPC нельзя.
6. `reconcileHolderExecution` повторно проверяет сохранённые receipts, части
   публикации и суммы totalReceived/totalAllocated/totalPaid/pendingBudget.
   Долг считается как allocated − paid. Необъяснённые изменения останавливают
   сверку; они не замалчиваются и не переписывают историю.

## Восстановление и роли

Миграция 017 создаёт отдельные таблицы конфигурации, планов и транзакций.
Для каждого токена действует транзакционная advisory-блокировка и частичный
unique index, допускающий только одну неизвестную транзакцию. Уникальность
chain/sender/nonce действует между областями. Конфигурация/планы доступны executor
только на чтение и вставку; изменять старый план через штатный API нельзя.
Подписанные байты недоступны `lp_api`/`lp_jobs`; RLS разделяет проекты.
Администратор БД и код executor остаются доверенными, checksum не защищает от
злоумышленника с полным SQL-доступом.

После обрыва до отправки восстанавливаются те же сохранённые байты. После обрыва
после отправки проверяется их хеш. Для неизвестного результата новая попытка
не создаётся. Finalized revert завершает конкретную попытку, но сохраняет долг;
новая транзакция с новым nonce допускается после исправления причины.
Повторная обработка завершённого receipt снова проверяет его каноничность.
Reorg/регресс finality вызывает ошибку, автоматического отката нет.

## Границы пакета

- `executionEnabled:false`: это библиотека и локальная EVM/PostgreSQL-репетиция,
  без production sender, фонового worker и финансового разрешения на запуск.
- [Следующий пакет](HOLDER_PERIODS_RECOVERY.md) добавил продвижение preparation
  после finalized seal и проверку двух периодов. Обработка пропущенного cutoff
  пока не определена. Fixture ledger не используется как разрешение.
- minimumPayment PW утверждён; тестовые суммы не заменяют его репетицию.
  Газовый бюджет и реальные адреса ещё не выбраны. Минимальная смена publisher
  реализована в managed v2, см. [управление фондом](HOLDER_GOVERNANCE.md).
- Replacement/cancel транзакции с тем же nonce не реализованы. Если nonce занят
  посторонней транзакцией, журнал останавливается; автоматически считать её
  выполнением или выпускать новую выплату нельзя.
- Внешние выплаты импортируются по известному хешу через trusted importer;
  добавлен ограниченный поиск Paid по сохранённому cursor (см. [репетицию PW](PW_LOCAL_REHEARSAL.md)). Необъяснённое расхождение
  счётчиков по-прежнему блокирует сверку.
- Сверка ограничена по числу транзакций (по умолчанию 200, максимум 2000),
  превышение требует явного следующего решения. Это не производственный
  индексатор и не оценка стоимости реального RPC.
- Pons runtime/cutoff, газ больших списков и восстановление ошибочной публикации
  остаются открытыми вопросами из предыдущих пакетов.

Продвижение периода, повторная месячная репетиция и импорт внешних выплат
реализованы в [следующем пакете](HOLDER_PERIODS_RECOVERY.md). До запуска нужны
выбор реальных адресов и production admission.
Публичный deployment и реальные отправки остаются отдельной задачей.

## Проверки

миграции выполняются дважды для проверки повторного запуска. Funding проходит
через реальный локальный collector/splitter, snapshot — через trusted admission.
Сценарии: неизменяемый план, роли/RLS, точные calldata и газовые пределы,
повтор/конкуренция, обрыв до/после отправки, finality lag, продолжение части
списка, отказ получателя после симуляции, восстановление, сверка долгов и
изменившийся канонический блок. Отдельные отчёты:
`.local/test-results/holder-execution-*/report.json`.
